> 日期：2026-09-09
> 对比对象：Claude Code、OpenCode、Grok Build、DeepWork（血缘来源）、trae-agent、Codex、Pi、commerce-agents、DeepSeek-Reasonix
> 参照材料：`F:\学习资料\agents-working-directory\` 下 1-* 源码与 2-* 解析文档集
> 说明：所有结论基于实际源码与解析文档，未修改任何参考材料

## 一、执行摘要

**一句话结论：aye-aye 的"远程运维工具链"是全部对比项目中最独特的资产，但它所运行的"Agent 运行时基础设施"（上下文治理、版本回溯、扩展机制、可观测性、评测）是这批项目里最薄的。**

两个必须先讲清楚的前提：

1. **定位不同，不能无脑照搬。** Claude Code / OpenCode / Grok / Codex / Pi / trae-agent 全是**本地代码 Agent**（改本地文件、跑本地命令）；aye-aye 是**远程运维 Agent**（连远程主机、管远程文件）。因此"本地文件编辑工具链"对它们是核心、对 aye-aye 是次要；而"SSH/SFTP 工具链"对 aye-aye 是命脉、它们一个都没有。

2. **aye-aye 的 ai-core 是 DeepWork 的 Java 翻译版**，而 DeepWork 本身只是一个约 5,000 行的教学级/早期实现。这意味着：aye-aye 继承的不是一个成熟 Agent 运行时的全貌，而是它的一个早期切片。后文 A.3 节逐项列出了"DeepWork 有而 aye-aye 没翻译"与"DeepWork 是空壳而 aye-aye 反而实现了"的双向差异。

### 差距总览

| 维度 | aye-aye | 业界最佳参照 | 差距 |
|---|---|---|---|
| Agent 主循环 | 有（maxSteps + 截断 4 层防御） | Claude Code / Grok | 基本对齐 |
| 工具系统 | 18 个工具，远程运维方向 | Claude Code 41 → 18~22 可见 | 基本对齐（方向不同） |
| **权限与安全** | 规则瀑布 + **fail-open 兜底** | Claude 9 步漏斗 + AST + 沙箱 | **严重缺失** |
| 上下文治理 | 有压缩（自研，DeepWork 空壳） | Claude 三层压缩 + 四层记忆 | 部分具备 |
| 多 Agent | 只读子代理，上限 4，单层 | Reasonix Fleet 2~64 并发 | 部分具备 |
| 错误恢复 | 指数退避 + 截断自适应 | Claude 熔断 + Fallback + 冷却 | 部分具备 |
| **版本回溯** | 仅远程备份/回滚 | OpenCode 独立 git 仓 revert | **严重缺失** |
| **扩展机制** | 无（硬编码注册表） | MCP / Skill / Plugin / Hook | **严重缺失** |
| **可观测性** | 无 | Claude OTel 三信号 + Perfetto | **严重缺失** |
| **评测体系** | 无 | trae-agent SWE-bench 对接 | **严重缺失** |
| 会话持久化 | SQLite | 各家均有 | 基本对齐 |
| 远程运维工具链 | **18 个工具中的 13 个** | **所有对比项目均无** | **领先** |

## 三、逐维度对比

### 3.1 Agent 核心循环

**aye-aye 现状**（`agent/AgentLoop.java`，297 行）
流式/非流式双入口 → 注入系统提示词 → `chatStream` 消费事件 → `TruncationHandler` 4 层防御 → 无 tool_call 则结束，否则执行工具 → 回灌消息 → 循环，`DEFAULT_MAX_STEPS = 10` 封顶。取消靠 `BooleanSupplier aborted` 轮询。

**业界做法**

| 项目 | 循环结构 | 终止 | 取消 |
|---|---|---|---|
| Claude Code | `query.ts` 单文件心脏 | 无 tool_call | AbortController，重试循环起止点检查 |
| OpenCode | 五层拆分：runner 状态机 + prompt 主循环 + processor 流式 + llm + tools | 助手完成且无待处理工具 | `Runner.cancel` + 工具内 `AbortSignal` |
| Grok | 三层套娃：`run_session`(Actor) → `handle_prompt` → `process_conversation_turn` | `TurnOutcome::{Completed, Cancelled, MaxTurnsReached}` | `InterjectionBuffer` 中途插话 |
| DeepWork | async generator yield `AgentEvent` | 同 aye-aye（同一套） | AbortSignal |

**差距：基本对齐。** aye-aye 的循环结构完整，截断 4 层防御（L1~L4）与 DeepWork 同构且是实打实的能力。

**可借鉴**
- **OpenCode 的 `DOOM_LOOP_THRESHOLD = 3`**：连续 3 次同工具 + 同输入 → 判定死循环并请求确认。aye-aye 只有 `maxSteps` 硬上限，无法区分"正常多步"与"卡死重复"。**成本极低，建议优先加。**
- **Grok 的 `InterjectionBuffer`**：允许用户在 Agent 执行中途插话改变走向。aye-aye 的 `aborted` 只能整体取消，不能"改道"。
- **Grok 的 TodoGate**：todo 未完成时催办（`max_fires_per_prompt` 默认 2），防止模型"说完就跑"。aye-aye 已有 `todo_write` 工具，但没有对应的催办机制——**工具有了，约束没有**。

### 3.2 工具系统设计

**aye-aye 现状：18 个工具**

| 类别 | 工具 |
|---|---|
| 元/编排（ai-core） | `tool_search`、`ask_user`、`spawn_subagents` |
| 主机 | `list_hosts` |
| SSH | `run_ssh` |
| SFTP（8 个） | `sftp_list`、`sftp_read`、`sftp_write`、`sftp_upload`、`sftp_remove`、`sftp_mkdir`、`sftp_rename`、`sftp_edit` |
| 远程增强 | `remote_grep`、`remote_backup` |
| 联网 | `web_search`（DeepSeek/Exa/Tavily 三后端）、`web_fetch` |
| 任务 | `todo_write` |

**关键发现：权限名单与实际实现脱节。** `PermissionEngine` 的三个名单里写了 `list_directory`、`glob`、`grep`、`run_shell`、`bash`、`delete_range`、`move_file` 共 7 个工具名，但全仓检索**没有任何对应的 Tool 实现**——这些是从 DeepWork 名单抄来的残留。反过来，实际注册的 `ask_user`、`spawn_subagents`、`remote_backup` **不在任何名单中**，落到 `default-allow` 直接放行（详见 3.3）。

**业界做法**

| 项目 | 工具定义 | 并发策略 | 结果处理 |
|---|---|---|---|
| Claude Code | `Tool.ts` 定义 14 个字段：含 `isReadOnly` / `isDestructive` / `isConcurrencySafe` / `checkPermissions` / `validateInput` / `maxResultSizeChars` | `partitionToolCalls()` 按 `isConcurrencySafe()` 分区：只读并行批、写入串行 | 超 `maxResultSizeChars` 存盘只回摘要，防上下文爆炸 |
| OpenCode | `Tool.Def{id, description, parameters: JSONSchema, execute}`，16 个 | — | `truncate.output` 智能截断 + 外部文件 |
| Grok | Rust `Tool` trait，`ToolKind` 枚举分类，32 个 | **同文件路径加锁**（`file_path/path/target_file` 相同则串行） | — |
| DeepWork | Zod schema + `execute` + 声明钩子 `resolveAffectedPaths`/`resolveCommandText`/`computeDestructiveHints` | `FileMutationQueue` 每路径异步锁串行写 | — |

**差距：基本对齐，但缺两个便宜的关键设计。**

**可借鉴**
1. **工具声明式元数据（Claude Code `isReadOnly`/`isDestructive`/`isConcurrencySafe`）**。aye-aye 目前靠三个硬编码名单 `List.of("sftp_write", ...)` 判断读写属性，新增工具必须手动登记——这正是 fail-open 的根因。改为**工具自带声明、权限引擎读取声明**，可从根本上消除"漏登记即放行"。
2. **`maxResultSizeChars` / 结果截断**。aye-aye 的 `sftp_read`、`remote_grep` 返回大结果时无上限保护，直接灌进上下文。`ContextCompactor` 是事后补救，Claude Code 是事前拦截——**两道防线都要有**。
3. **Grok 的同路径加锁**。aye-aye 已有 `FileMutationQueue`，但需确认是否覆盖 SFTP 远程路径写。

### 3.3 权限与安全（差距最大）

**aye-aye 现状**（`permission/PermissionEngine.java`，281 行）
规则瀑布 `M1_PERMISSION_RULES` 按序匹配，第一条返回非 null 决策生效。共 7 条规则 + **`default-allow` 兜底**。

**业界做法**

| 项目 | 机制 | 兜底 |
|---|---|---|
| Claude Code | **9 步漏斗**：deny → must-ask → `checkPermissions` → 交互 → 内容规则 → 受保护路径 → bypass → allow → ASK | **ASK（fail-closed）** |
| OpenCode | Effect 规则引擎：通配匹配 + agent/session ruleset 合并 + `allow/deny/ask` + `Deferred` 异步等待 + `once/always/reject` 语义 | `ask` |
| Grok | 提示词 `action_safety` + 运行时 `PermissionReject` + 工具 `ToolScope::Read` | 拒绝 |
| **aye-aye** | 规则瀑布 + **`default-allow`** | **Allow（fail-open）** |

**这是本次对比中最严重的差距。** 具体表现：

1. `PermissionEngine.java:190-195` 兜底规则 `matches` 恒为 true 排在最后 → 未登记工具一律放行
2. `:205-224` 规则 `matches`/`decide` 抛异常时 `catch → continue` → 最终仍落到放行，**规则出错 = 安全降级**
3. 实际注册的 `ask_user`、`spawn_subagents`、`remote_backup` 三个工具不在任何名单 → 零确认执行
4. 高危命令黑名单（`:56-66`）全是 Windows 形态（`rd /s`、`format X:`、`reg delete`、`iex`），而产品是 Linux 运维 → `rm -rf /`、`mkfs`、`dd of=/dev/sda` 不在硬拒列表
5. 无沙箱、无命令 AST 分析

**Claude Code 的 Bash 安全分析尤其值得单独说**（`28 - Tree-Sitter Bash AST 安全分析完整解析.md`）：
- 自研纯 TS 递归下降 Parser（约 4,200 行，零原生依赖），预算 `MAX_NODES=50000`、`TIMEOUT_MS=50`
- 识别 18 种危险节点：命令替换 `$(...)`、进程替换、变量展开、子 shell、for/while/if/case、heredoc、管道、重定向、glob、后台任务
- 引号上下文三态：Unquoted / SingleQuoted（最安全）/ DoubleQuoted
- **遵循 FAIL-CLOSED：无法识别 → UNSAFE**
- 另有 23 个安全验证器（`bashSecurity.ts` 2,593 行），覆盖 ANSI-C 引号 `$'\x6d'`、Locale 引号、反斜杠、回车混淆、Unicode 空白、IFS 注入、`jq system()` 等绕过手法

**改进优先级（按性价比）**
1. 兜底改 `Confirm` —— 一行改动，消掉 80% 风险
2. 工具自带危险等级声明，替换硬编码名单 —— 消除漏登记
3. 补 Linux 高危命令 Deny 黑名单 —— 对齐产品定位
4. Bash AST 分析 —— 工作量大，建议先用正则黑名单 + 后续迭代

### 3.4 上下文与记忆管理

**aye-aye 现状**：`context/ContextCompactor.java`（285 行），`BUDGET_RATIO=0.72`、`TARGET_RATIO=0.5`、`DEFAULT_CONTEXT_WINDOW=128_000`，LLM 语义总结 + 抽取式兜底。

**值得肯定**：这是 **aye-aye 反过来超越 DeepWork 的地方**——DeepWork 的 `ContextCompressor` 是注释写着"未来实现"的空壳，aye-aye 真正实现了它。

**Claude Code 的做法（三层压缩 + 四层记忆）**

| 层 | 机制 | 触发 |
|---|---|---|
| 压缩 L1 Snip | 纯算法按重要性打分裁剪（用户消息/最近工具结果高分，被覆盖的旧 Read 零分） | 每轮循环前 |
| 压缩 L2 微压缩 | 时间型：无活动 `gapThresholdMinutes=60` → 保留最近 5 个工具结果；缓存型：删 `cache_edits` 对应结果 | 自动 |
| 压缩 L3 自动压缩 | **唯一用大模型**，9 维度结构化摘要，压缩比约 10:1（167k→17k） | `有效窗口 - 20000(输出预留) - 13000(缓冲)` |
| 记忆 L1 | `CLAUDE.md` 环境记忆，5 级优先级加载，支持 `@include` 与 `paths:` 条件规则 | 启动 |
| 记忆 L2 | `~/.claude/projects/<项目>/memory/*.md`，4 类型，Sonnet 筛选最多 5 条注入 | 按需 |
| 记忆 L3 | 内存 messages 数组 | — |
| 记忆 L4 | `~/.claude/session-memory/<id>/notes.md`，后台 Agent 提取 | token/工具次数超阈值 |

**差距：部分具备。** aye-aye 有压缩（约等于 Claude 的 L3），但缺 L1 打分裁剪、L2 微压缩，更缺**记忆系统**。

**可借鉴（成本从低到高）**
1. **L2 时间型微压缩**：60 分钟无活动则把旧工具结果替换为占位符。约 20 行代码，效果显著。
2. **记忆文件机制**：对运维场景价值极高——把"这台机器的 nginx 配置在 /etc/nginx/conf.d/，重启用 systemctl reload"这类主机知识沉淀成 `HOSTMEMORY.md`，按 host_key 注入 prompt。这是 aye-aye 相比编码 Agent 的**场景红利**，Claude Code 的 CLAUDE.md 机制可直接改造。
3. **L3 压缩用 forked agent 共享提示缓存**省钱——aye-aye 单用户场景优先级不高。

### 3.5 多 Agent 编排

**aye-aye 现状**：`tools/SubAgentsTool.java`，`spawn_subagents` 并行派发 2~4 个**只读**子代理，单层深度、不可嵌套、不可向用户确认，超时 300s。

**业界做法**

| 项目 | 机制 |
|---|---|
| Claude Code | `AgentTool` 派生，内置 5 种（General-Purpose / Explore 只读 / Plan / **Verification 对抗验证**输出 `VERDICT: PASS/FAIL/PARTIAL` / Guide）。Fork 继承父上下文共享提示缓存，Fresh 空历史 + 简报。Mailbox IPC + 13 种结构化协议消息 |
| Grok | Orchestrator 委派，`explore`/`plan` 只读，最大嵌套深度 1 层 |
| **Reasonix** | **Fleet 并行 2~64 个 profile 感知子代理，写任务需预声明不重叠 `write_paths`，支持后台 fleet job + `wait` 收集** |
| DeepWork | **无子 Agent 概念** |

**差距：部分具备。** aye-aye 的 SubAgentsTool 已经是超越 DeepWork 的自研能力，但相比 Reasonix 缺 `write_paths` 写隔离与后台 job。

**可借鉴**
1. **Reasonix 的 `write_paths` 预声明不重叠**：aye-aye 子代理当前强制只读，其实可以放开写——前提是每个子代理预先声明写路径且不重叠。这对"批量巡检多台主机后各自生成报告"场景直接可用。
2. **Claude Code 的 Verification 子 Agent**：对抗式验证，3 个以上文件编辑后强制启用。运维场景可改造为"执行完变更命令后，派一个独立子代理验证结果是否符合预期"。

### 3.6 错误处理与弹性恢复

**aye-aye 现状**（`llm/LlmClient.java`）：指数退避 `sleep(500L << attempt)`，connect 15s，整体超时 10 分钟。

**Claude Code 的做法**

| 机制 | 参数 |
|---|---|
| 指数退避 | 500→1000→2000→4000→8000→16000→32000ms 封顶，最大 10 次，随机抖动 ±25% 防惊群，最大总等待约 193.5s |
| 529 Overloaded | `MAX_529_RETRIES=3`；前台源重试 3 次后 Fallback，非前台源立即抛 `CannotRetryError` |
| Fast Mode 冷却 | `Retry-After >= 20s` → 冷却 10~30 分钟 → 切标准速度 |
| 模型 Fallback | 连续 3 次 529 → `FallbackTriggeredError` → 切 `fallbackModel` |
| 输出截断恢复 | `max_tokens` 溢出自动提升 8K→16K→32K→64K，最多 3 次，`FLOOR=3000`，**不消耗用户重试次数** |
| 服务端尊重 | 实际等待 `max(服务端 Retry-After, 本地退避)`；`x-should-retry:false` 立即放弃 |
| 熔断 5 类 | 529 连 3 次 / Fast Mode 冷却 / 非前台 529 / `x-should-retry:false` / Graceful Shutdown |

**差距：部分具备。** aye-aye 有退避和截断自适应（`TruncationHandler` 4 层），但缺抖动、缺熔断、缺模型 Fallback、缺服务端 `Retry-After` 尊重。

**可借鉴（成本极低）**
1. **退避加 ±25% 随机抖动** —— 一行改动，防惊群
2. **尊重服务端 `Retry-After` 与 `x-should-retry:false`** —— 避免无谓等待与无效重试
3. **模型 Fallback** —— aye-aye 已有多模型管理（`/api/models` CRUD），接一个 fallbackModel 字段即可

### 3.7 版本回溯（严重缺失）

**aye-aye 现状**：有 `RemoteBackupTool`（远程备份 + 回滚），但是**运维语义的粗粒度备份**，不是 Agent 执行过程的操作级回溯。

**业界做法**

| 项目 | 机制 | 粒度 |
|---|---|---|
| **OpenCode** | 建**独立 git 仓库**（`Global.Path.data/snapshot/<projectID>/<hash>`，用 `--git-dir`/`--work-tree`，不污染用户仓）；`track()` = `git add --all` + `git write-tree` 生成 tree hash；`revert({sessionID, messageID, partID?})` 收集目标后所有 patch → `git checkout <hash> -- <file>`；`unrevert()` = `git read-tree` + `checkout-index -a -f` | **消息级 / part 级** |
| **Grok** | 多域 Rewind：FS 域（`FileStateTracker` 按 prompt_index 存 before/after 快照，冲突检测 Deleted/Created/ModifiedExternally）+ Git 域（HEAD SHA + staged paths，`stash` → `reset --soft`）+ Hunk 域（**行级 Accept/Reject**）；三域独立开关，任一失败不阻断其他 | prompt_index 级 + 行级 hunk |
| Claude Code | 版本回溯 + Worktree 隔离 | — |

**差距：严重缺失。** 对运维场景而言，这比编码场景**更危险**——Agent 在远程主机上执行 `sftp_write`、`run_ssh` 是直接改生产环境，一次误操作的代价远高于改本地代码。

**建议路线（先轻后重）**
1. **第一阶段**：`sftp_write`/`sftp_edit`/`run_ssh` 执行前自动保存文件快照到 SQLite（或本地 `.aye/snapshots/`），提供"回滚上一步"。成本低，立刻可用。
2. **第二阶段**：借鉴 OpenCode 的独立 git 仓思路，按 session 建仓，tree hash 标识，支持 `revert`/`unrevert`。
3. **第三阶段**：Grok 的多域思路——FS 域（本地快照）+ SSH 域（远程文件快照）+ 命令域（记录执行的命令及逆操作）。

### 3.8 扩展机制（严重缺失）

**aye-aye 现状**：工具硬编码注册在 `BuiltinTools.createToolRegistry()` 与 `AgentBeansConfig.java:234-248`，加工具要改 Java 代码重新编译。

**业界做法**

| 项目 | 扩展点 |
|---|---|
| Claude Code | **MCP**（6 种传输：stdio/sse/sse-ide/http/ws/sdk，工具命名空间 `mcp__<server>__<tool>`，OAuth PKCE、重连 `MAX_RECONNECT_ATTEMPTS=5`、7 种配置作用域、动态能力热更新）+ **Skill/Plugin** + **Hook**（PreCompact/PostCompact/SessionEnd/权限钩子/MCP Elicitation） |
| commerce-agents | **Skill（SKILL.md 组合单元）+ Plugin（可插拔扩展点，含 commands/skills）**，按业务域拆分 |
| Pi | 库化 `@earendil-works/pi-ai`，可被其他项目直接依赖 |
| OpenCode | `registry.ts` 动态注册 + 插件 |
| Grok | 多命名空间兼容（GrokBuild / GrokBuildHashline / OpenCode / Codex 四套互斥） |

**差距：严重缺失。** 这是"从能用到好用"的分水岭。

**建议**：优先做 **Skill（提示词级）** 而非 MCP（协议级）。
- Skill 只需：约定目录 + Markdown 描述 + 加载器，工作量约 1~2 天，对运维场景价值极高（"K8s 排障手册"、"Nginx 配置检查"等运维知识可直接以 Skill 形式注入）
- MCP 工作量大，且 aye-aye 是单用户桌面应用，外部 MCP server 需求弱；**除非要接入内部系统**，否则优先级放后

---

### 3.9 可观测性（严重缺失）

**aye-aye 现状**：无。仅有 `[AiDiagnose]` 打 stderr（`LlmClient.java:63-67,172-178`）。

**Claude Code 做法**：OTLP 三信号（Metrics 始终启用 / Logs / Traces 门控）+ Perfetto 本地追踪（Chrome Trace Event 格式，`MAX_EVENTS=100000`，`STALE_SPAN_TTL=30min`，三重退出保障）+ Session Tracing 4 类 Span（`interaction`/`llm_request`/`tool`/`hook`，`AsyncLocalStorage` 自动传播）+ 成本指标（单次会话累计 >$5 提醒）+ Kill Switch 远程关停。

**建议（最小可用集）**：aye-aye 不需要 OTel 全套，但**至少需要一张 Agent 运行追踪表**：每次会话记录 `session_id / step / llm_latency / tool_name / tool_duration / token_in / token_out / 是否命中压缩 / 权限决策`。存 SQLite 即可，前端加一个"会话详情"面板。**这既是可观测性，也是调试 Agent 行为的基础设施**——没有它，优化 Agent 全靠猜。

---

### 3.10 评测体系（严重缺失）

**aye-aye 现状**：无。

**业界**：trae-agent 的 `evaluation/` 直接对接 SWE-bench / SWE-bench-Live / Multi-SWE-bench（7 语言 1,632 实例），Docker 复现环境跑 patch 对照真实答案评分 + patch 遴选。Pi 有独立 `packages/evals`。

**建议**：运维场景没有现成 benchmark，但可以自建**小型回归集**：20~30 条典型任务（"查 nginx 错误日志"、"磁盘满了怎么办"、"批量重启服务"），人工标注期望工具调用序列，每次改动 ai-core 后跑一遍。不需要自动化评分，先有"改动前后对比"的能力即可。

---

### 3.11 会话与持久化

**aye-aye**：SQLite 存储会话/消息/主机/审计/设置/快捷指令/模型+key，含轻量 schema 迁移。**基本对齐**。

值得注意的是：aye-aye 的 `SqliteAuditLedger` 实现了 DeepWork 只是内存版的 `InMemoryAuditLedger`——**这是又一个反超血缘来源的地方**。

## 四、aye-aye 能力矩阵

### 已有（18 个工具 + 平台能力）

| 能力域 | 具体能力 |
|---|---|
| 主机管理 | CRUD + 拖拽排序，凭据 Electron safeStorage 加密 |
| SSH | 长效会话 + 一次性命令 + 交互式终端（WebSocket + xterm.js + 心跳） |
| SFTP | list / read / write / upload / download / remove / mkdir / rename / edit（8 个工具） |
| AI 对话 | SSE 流式，事件 `start → (thinking/text/tool_call/tool_result)* → (error/done)` |
| Agent 运行时 | 主循环 + 截断 4 层防御 + 上下文压缩 + 权限引擎 + 审计账本 |
| 编排 | `spawn_subagents` 并行只读子代理、`ask_user` 主动询问 |
| 联网 | `web_search`（DeepSeek/Exa/Tavily 三后端）+ `web_fetch` |
| 任务 | `todo_write` 多步进度 |
| 运维增强 | `remote_grep`、`remote_backup`（备份/回滚） |
| 平台 | 会话历史、模型 CRUD + key 脱敏、快捷指令、设置 kv、审计查询/统计 |

### 缺失（按重要性排序）

| # | 缺失项 | 参照 | 影响 |
|---|---|---|---|
| 1 | **权限 fail-closed** | 全部对比项目 | 未登记工具零确认执行 |
| 2 | **操作级版本回溯** | OpenCode / Grok | 远程误操作不可撤销 |
| 3 | **扩展机制（Skill/MCP/Hook）** | Claude Code / commerce-agents | 加能力必须改代码重编译 |
| 4 | **可观测性** | Claude Code | 无法诊断 Agent 行为 |
| 5 | **记忆系统** | Claude Code CLAUDE.md | 主机知识无法沉淀复用 |
| 6 | 工具结果大小上限 | Claude Code `maxResultSizeChars` | 大输出撑爆上下文 |
| 7 | 死循环检测 | OpenCode `DOOM_LOOP_THRESHOLD` | 卡死重复消耗 step |
| 8 | 熔断 + 模型 Fallback | Claude Code | 上游故障时长等待 |
| 9 | 本地文件工具 | DeepWork read/write/edit | 无法操作本机文件（场景相关，优先级可低） |
| 10 | 评测体系 | trae-agent / Pi | 改动无回归保障 |

### 独有优势（不要妄自菲薄）

1. **SSH/SFTP 远程工具链（13/18 工具）** —— 全部对比项目都是本地代码 Agent，**没有一个具备远程主机操作能力**。这是 aye-aye 最坚实的护城河。
2. **交互式终端 WebSocket** —— 人机协同运维的关键入口，编码 Agent 不需要，运维 Agent 必需。
3. **`ContextCompactor` 真正实现** —— DeepWork 血缘里是空壳，aye-aye 补齐了。
4. **SQLite 持久化审计** —— DeepWork 是内存版，aye-aye 落地了。
5. **`SubAgentsTool`** —— DeepWork 完全没有的自研能力。
6. **远程备份与回滚** —— 运维场景刚需，对比项目均无。
7. **Java 实现** —— 与 Electron sidecar 同进程，无 Node/Python 运行时依赖，部署形态干净。

## 五、借鉴优先级路线图

判断标准：**「对运维场景的适用度」×「实现成本」**，而非"Claude Code 有就要有"。

### 第一批：高价值 · 低成本（1~2 周）

| 项 | 来源 | 成本 |
|---|---|---|
| 权限兜底改 fail-closed + 工具自带危险等级声明 | 全部项目共识 | 小 |
| 补 Linux 高危命令 Deny 黑名单 | — | 小 |
| 工具结果大小上限 + 截断存盘 | Claude Code | 小 |
| 死循环检测（连续 3 次同工具同输入） | OpenCode | 小 |
| 退避加随机抖动 + 尊重 `Retry-After` | Claude Code | 极小 |
| 微压缩（60 分钟无活动清理旧工具结果） | Claude Code L2 | 小 |
| Agent 运行追踪表（SQLite + 详情面板） | Claude Code 简化版 | 中 |

### 第二批：高价值 · 中成本（1~2 月）

| 项 | 来源 | 成本 |
|---|---|---|
| **操作级版本回溯**（先快照回滚，后独立 git 仓） | OpenCode | 中 |
| **Skill 机制**（Markdown + 目录约定 + 加载器） | commerce-agents / Claude Code | 中 |
| **记忆系统**（按 host_key 的 HOSTMEMORY.md） | Claude Code CLAUDE.md 改造 | 中 |
| 子代理 `write_paths` 写隔离 + 后台 job | Reasonix Fleet | 中 |
| 模型 Fallback + 熔断 | Claude Code | 中 |
| 小型回归评测集（20~30 条） | trae-agent 思路 | 中 |

### 第三批：视需求而定

| 项 | 说明 |
|---|---|
| MCP 协议接入 | 单用户桌面场景需求弱，除非要接内部系统 |
| Bash AST 安全分析 | 价值高但工作量大（约 4,200 行 parser），先用正则黑名单过渡 |
| OS 级沙箱 | 运维场景本就要连远程机，本地沙箱价值有限；**更该做的是限制 Agent 能碰哪些主机** |
| OTel 全套 | 单用户场景，本地追踪表足够 |
| 本地文件/命令工具 | 翻译 DeepWork 的 read/write/edit 不难，但对远程运维场景非刚需 |

### 明确不建议照搬

- **Claude Code 的 41 个工具规模** —— aye-aye 是垂直运维，18 个工具够用，堆工具会稀释模型注意力
- **Grok 的 Goal 监督环 + TodoGate** —— 强自主模式对"改生产环境"的运维场景风险过高，除非配合强权限
- **Claude Code 的 auto 模式 AI 分类器** —— 用模型审模型，在 fail-open 现状下会放大风险
