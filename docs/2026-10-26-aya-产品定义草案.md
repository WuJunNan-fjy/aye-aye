# aya 产品定义草案

日期：2026-10-26  
更新：2026-10-27  
状态：新项目需求讨论记录，尚未进入实现  
名称：沿用讨论中的 aya；当前仓库为 aye-aye，本文不代表已经决定更名。

本文区分用户已经确认的需求、据此提出的产品设计，以及尚未决定的事项。目标是从零开始建设一个新项目；当前 aye-aye、ZCode、deepseek-harness、其他本地源码与 GitHub 开源项目均可作为调研和复用来源。本文不代表现有代码已经具备这些能力。

## 1. 已确认的产品目标

aya 是桌面打开时可用的服务器管家。用户希望它了解自己的各个项目，能够操作本地项目、准备服务器环境、完成部署，并集中展示项目和服务器的实际运行情况，减少人工运维工作。

用户同时重视 Agent 办事能力、产品使用体验和自己持续理解维护代码的能力。

### 运行边界

- 桌面应用运行期间开展项目管理、部署、状态检查和自动发布。
- 不要求桌面关闭后继续监控、自动修复或触发新的部署。
- 已经部署到服务器的应用独立运行，不依赖 aya 桌面保持打开。
- 重新打开时核对实际状态，保留最后检查时间；连接失败时不把旧的正常状态当作当前事实。
- 正在执行部署时关闭桌面的处理方式尚待设计。

### 主要项目类型

- Java 后端、Vite 前端，以及数据库和 Redis 等依赖。
- aya 应能够安装和配置 Java、Nginx、数据库、Redis 等所需环境。
- 支持同一 Java 后端在多台服务器运行，由 Nginx 分发请求。
- 支持前端、后端或不同服务分别部署到不同服务器。
- 同时管理多个项目与多台服务器；项目和服务器之间是多对多关系，不以固定数量设计模型。性能边界在实现后验证。

## 2. 已认可的产品模型

### 项目与服务器：两个视角，一套关系

项目视角回答：项目依赖什么、部署在哪里、各实例运行什么版本、是否正常、最近发布的结果是什么。

服务器视角回答：机器上有哪些组件和共享服务、关联哪些项目、资源与端口如何使用、异常会影响谁。

两个视角由同一份部署关系生成，支持相互跳转，避免分别维护配置。

### 单独记录部署实例

一个后端组件在两台服务器运行，对应两个部署实例。每个实例独立记录服务器、版本、运行状态、日志位置和检查时间。发布部分成功时，应能辨别各实例的真实情况。

### 共享基础设施记录依赖

Nginx、数据库、Redis 等服务记录所在服务器、版本、管理归属及使用它们的项目。项目所用数据库、账号、缓存配置和域名路由分别关联。

aya 应自动发现并维护这些关系，避免要求用户手工填写所有底层信息。调整共享服务时，应能解释影响范围。

### 项目资料可核验、可更新

保存已经验证的构建方式、部署方案、依赖关系、发布记录与故障处理记录。聊天记录可以提供线索，正式项目资料和运行状态需要通过项目文件、工具结果和实际检查更新。

## 3. 已确认的发布入口

### 主要入口：本地改完后让 aya 更新

用户在本地修改项目，再告诉 aya“更新这个项目”。aya 以当前本地代码为来源，形成可定位的本次源码快照或产物标识，执行构建、发布和验证，并保存结果。

该入口不要求用户必须先提交 Git；具体快照方式尚待设计。

### 可选入口：指定 Git 分支自动发布

按项目启用，在 aya 运行期间检测指定分支的更新，以明确的 Git 提交作为发布来源。

两种入口共用发布流程和发布记录。同一项目环境的发布排队执行，避免不同触发相互覆盖。检测机制、频率和重复提交去重方式尚待设计。

## 4. 已确认的部署失败修复边界

| 修改内容 | 处理方式 |
| --- | --- |
| 构建脚本 | 为完成当前部署，可自动修复 |
| 依赖 | 为完成当前部署，可自动调整 |
| 部署配置 | 为完成当前部署，可自动修复 |
| 业务逻辑、业务功能 | 修改前需要用户确认 |

判断依据包含改动实际影响，而不只看文件类型。若某项依赖或配置调整会改变业务逻辑或功能，也属于需要确认的范围。

以上是当前已发起部署的修复权限，不等于已经确定启动应用时自动修复所有服务器问题的策略。

## 5. 验证：当前解释与预留能力

### 自动工程验证：作为发布闭环的设计基础

根据已认可的可靠状态检查与发布流水线设计，保留以下自动检查方向：

- 构建命令是否成功，产物是否存在且对应本次发布。
- 目标实例是否启动，服务是否通过配置的健康检查。
- 实例实际运行的版本是否与本次发布一致。
- 多实例发布中哪些成功、哪些失败，整体结果是否需要继续处理。

“已发布”应有执行结果和检查证据支持，不能仅根据模型声明或阶段工具输入判定。具体检查标准、等待与重试策略尚待设计。

### 人工验证：先预留，是否实现后续再定

当前将用户所说的“人为验证”理解为发布后的人工业务验收。先预留扩展位置，暂不把具体人工验收界面或强制审批流程列为首版必交付。

是否实现、验收内容以及是否阻塞后续步骤，后续讨论。该项延期不等于取消自动构建检查与服务健康检查，也不影响业务代码修改前需要确认的规则。

## 6. 初步交互建议，尚未定稿

- 项目为主要入口：查看项目资料、组件、实例、状态和发布记录，并下达更新任务。
- 服务器为资源与影响范围入口：查看承载内容、依赖关系和机器状态。
- 任务页集中展示环境安装、发布与故障处理，支持查看进度、补充要求和停止。
- 首次接入时由 aya 读取项目和检查机器，生成项目档案与可复用部署方案，后续按变化调整。

旧 aya 的七阶段进度可以作为执行过程展示的参考，但新项目的资料、实例状态和发布记录需要独立设计。

## 7. 技术倾向与待设计事项

用户不希望用 Java 实现新 aya，熟悉 Java、JavaScript 和 TypeScript。此前源码审阅已经确认，ZCode 与 deepseek-harness 的主要 Agent 运行机制由 TypeScript/Node 实现，可以参考其职责边界。

TypeScript 主导的实现是目前建议方向；框架、模块划分、开源内核选型及新项目存放位置尚未决定。根据各组件的许可证与技术适配情况，可以直接依赖开源组件、复用相应代码或参考设计。

以下事项不应在实现中擅自视为已定：

- 服务器环境的安装方式、原生进程或容器、共享服务隔离方式。
- 多实例发布顺序、流量切换、故障恢复与回滚方案。
- 数据库结构变更与应用版本发布的配合方式。
- 初次部署与重复发布各自的确认体验。
- 部署进行中关闭桌面、重新打开后的继续与核对机制。
- 已运行项目发生异常时，自动诊断与自动修复的具体范围。
- 人工业务验收功能的具体实现。

## 8. 新项目的设计启示

1. 研究可直接复用的 Agent 循环、统一工具执行与权限检查、会话事件和后台任务组件。
2. 建立项目、组件、部署实例和共享服务之间的持久关系，使产品能够长期管理运行中的应用。
3. 让部署状态与实际执行、健康检查结果关联，避免阶段声明与真实结果脱节。
4. 两种发布入口使用同一执行流程，保留本次来源和实例结果，形成可复用、可追踪的发布记录。
5. 在明确核心交互和数据边界后，选取合适的开源组件并独立设计 TypeScript 实现。旧项目作为可研究、可复用的材料，不设迁移旧系统或旧数据的目标。
