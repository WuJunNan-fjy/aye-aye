# 动态部署设计（剧本 + 施工单 + 部署档案）

日期：2026-09-27
状态：设计已与用户逐节确认，待书面评审，未进入实现
前置文档：2026-09-20-小白一键部署设计.md（本设计取代其「固定 7 阶段」模型，工作区、本机执行、直传等能力全部继承）

## 0. 目标与范围

### 0.1 要解决的问题

现有「小白一键部署」把部署流程焊死在四层代码里：ChatService 的 7 步提示词、`DeployStage` 七值枚举、账本预铺 7 格、前端 7 段 Dock。实测暴露两个问题：

1. **窄**：只覆盖一条黄金路径（本地 npm/mvn 构建 → tar → 上传解压 → 三种固定启动形态）。Docker、Compose、Go 二进制、需要写配置/迁库的项目走不下去，只能在多轮对话里手工补。
2. **碎**：7 步只是写给 AI 的台词，不是系统持有的计划。一次部署被拆到多段对话里靠 AI 翻历史脑补续摊，用户对部署没有「整件事」的载体。数据库 `plan_json` 字段早已预留但从未写入。

目标形态：

```
说「部署这个项目」→ AI 按剧本检测项目 → 产出一张看得见的施工单（步骤按项目长出来）
→ 用户确认一次（可改端口/目录）→ 按单执行、逐步记账、失败即停
→ 关掉明天再开，这次部署还在，点「继续/再部署」接着跑
```

部署的单位从「一次次对话」变成「一张计划卡的一生」。

### 0.2 明确做

1. **剧本库**：后端 classpath 内置 Markdown 部署剧本（skill 形态），分栈编写、AI 按需加载；新增栈只加 md 文件，不改 Java。
2. **动态计划**：AI 检测后产出结构化施工单（步骤数组、产物、目标目录、端口、启动形态），落库为权威契约。
3. **首停后续免**：计划首次必须确认；同项目同主机且计划签名未变的「再部署」一键执行不打断；计划变化重新确认。
4. **消息内施工单卡**：替代输入区上方常驻 7 段 Dock；待确认 → 执行中 → 终态三态，随会话持久化。
5. **右侧「部署」页签**：跨会话部署列表、详情、中断部署「继续部署」、成功部署「再部署」。
6. **栈覆盖**：静态站、Node、Java-jar 三种剧本；新增受控 Docker/Compose 工具；剧本外动作以 run_ssh 兜底（逐条走高危确认引擎）。
7. **失败可续**：步骤失败即停并挂起 turn；修复重试与跨会话续跑都以冻结计划 + 步骤账本为依据。

### 0.3 明确不做（本期）

- 不做 systemd service、远程数据库迁移自动化、域名/HTTPS/反向代理、K8s。
- 不做多主机/多实例批量部署、定时自动部署、私有仓库凭证管理。
- Docker 工具不支持任意宿主机目录挂载、`--privileged`、自定义网络（有需要走 run_ssh 兜底确认）。
- 不改动 ai-core、dsh、旧前端；浏览器端不提供部署能力（沿用桌面版限定）。

## 1. 总体架构：三层分离

| 层 | 载体 | 回答的问题 | 可变性 |
|---|---|---|---|
| 剧本层 | `resources/deploy-playbooks/*.md` | 这类项目**一般怎么**部署 | 加 md 即扩展，开源可贡献 |
| 计划层 | `deploy_runs.plan_json`（结构化） | **这一次**部署具体做哪几步 | 每次部署一份，确认后冻结 |
| 执行层 | 现有工具族 + 2 个新工具 | 步骤**怎么**安全地执行 | 白名单构造命令 + 确认引擎兜底 |

部署仍复用现有对话主循环（ChatService + AgentLoop + 事件日志 + SSE + PendingInteractionHub），不另起编排引擎。

### 1.1 剧本层

`apps/termmind-server/src/main/resources/deploy-playbooks/`：

| 文件 | 内容 |
|---|---|
| `00-overview.md` | 总纲：检测决策树（package.json/pom.xml/Dockerfile/静态文件的判定顺序与信号）、出计划纪律、确认纪律、失败即停纪律、工具清单与首选通道原则。短，绑定工作区时直接注入系统提示，**取代现有 `DEPLOY_SUPPLEMENT` 7 步台词** |
| `static-site.md` | 纯静态/Vite/React build 产物：跳过 prepare 或只 install，build 后打包 dist，`python3 -m http.server` 或 nginx 提示 |
| `node.md` | Node 服务：install/build（如有）、生产依赖处理、`node app.js` 启动、环境变量与端口约定 |
| `java-jar.md` | Maven/Gradle：`mvn package`/`gradle bootJar`、定位 jar、`java -jar` 启动 |
| `docker.md` | Dockerfile 构建运行与 compose 项目：何时用受控 docker 工具、何时降级 run_ssh |
| `generic.md` | 兜底纪律：剧本未覆盖的步骤必须走 run_ssh，在计划中标 `risk` 说明，逐条等用户确认；禁止绕过部署工具族手工散放文件 |

AI 通过只读工具 `deploy_playbook(stack)` 按栈取对应 md（检测前只持总纲，避免上下文浪费；未来剧本增多时不膨胀）。

### 1.2 计划层

`plan_json` 从闲置字符串升级为结构化施工单：

```json
{
  "version": 1,
  "stack": "static-vite",
  "title": "my-blog 部署计划",
  "steps": [
    {"id": "s1", "kind": "detect",  "label": "看懂项目"},
    {"id": "s2", "kind": "build",   "label": "构建", "command": "npm run build", "local": true},
    {"id": "s3", "kind": "package", "label": "打包 dist.tar.gz", "artifact": "dist.tar.gz"},
    {"id": "s4", "kind": "upload",  "label": "上传并解压", "remoteDir": "/root/termmind-apps/my-blog"},
    {"id": "s5", "kind": "verify",  "label": "启动并验活", "port": 8080, "startForm": "python-http"}
  ],
  "target": {"hostKey": "host-xxx", "remoteDir": "/root/termmind-apps/my-blog", "port": 8080},
  "signature": "<sha256>"
}
```

- `kind` 为后端白名单枚举：`detect / prepare / build / package / upload / extract / start / verify / docker / generic`；`label` 是给用户看的大白话，可自由写。
- **签名**输入 = stack + 每步 kind 及关键参数（command/remoteDir/startForm/port/mode）+ target；不含 label、summary 等文案。签名决定「再部署」能否免确认。
- 步骤状态仍存 `stages_json` 列（列名保留、语义改为 `Map<stepId, StepState>`），避免无谓迁移。
- run 状态机：`draft`（计划草稿）→ `awaiting_confirm` → `confirmed`（已确认，执行中）→ `done` / `failed`；失败后用户触发重试回到 `confirmed`。
- **中断不另设状态**：turn 被用户取消或断连时，run 仍停在 `confirmed`（某步可能残留在 running）。「继续部署」捞起这类 run 时，先把残留 running 步重置为 pending，再从该步续跑。

### 1.3 执行层

| 工具 | 处置 | 说明 |
|---|---|---|
| run_local_async / local_job_poll / edit_local_file | 保留 | 本机检测、构建、排错 |
| deploy_upload / deploy_extract_remote / deploy_probe_remote | 保留 | 构造安全命令通道，剧本中的首选 |
| deploy_start_remote | 保留增强 | 三种固定形态不变；新增 run 状态校验（见 3.2） |
| deploy_stage | **替换为 deploy_step** | 步骤 id 来自动态计划，不再收枚举 |
| deploy_playbook | **新增** | READ：按栈取剧本 md |
| deploy_plan | **新增** | READ 外观但写账本：提交/修订计划，触发确认挂起 |
| deploy_docker_remote | **新增** | EXECUTE：受控 docker/compose（见 4） |

## 2. 交互流程

### 2.1 首次部署

1. 绑定工作区后，系统提示注入 `00-overview.md` 总纲。
2. 用户说「部署这个项目」。AI 用 run_local_async 检测项目，调 `deploy_playbook("static-site")` 取剧本。
3. AI 调 `deploy_plan` 提交结构化计划。后端校验通过 → 计算签名 → 落库 `awaiting_confirm` → 经 **PendingInteractionHub 挂起本轮 turn**（复用现有 confirmation 通道，新增负载类型 `deploy_plan`，不新造挂起机制）。
4. 前端在对话中渲染 **DeployPlanCard 待确认态**：项目/栈、步骤清单、产物、远程目录与端口（可直接改）、「确认，开始部署」「取消」。
5. 用户确认 → 回调放行 turn，run 置 `confirmed`；AI 收到「计划已确认」，逐步执行，每步开始/结束调 `deploy_step` 记账，卡片原地推进。
6. 卡片上改端口/目录后确认：回调携带修改值，后端重新校验并以新参数落为 version+1（用户的修改动作即确认，不二次打断）。对话中口头改计划：AI 重新调 `deploy_plan`（version+1），再次走确认。

### 2.2 再部署（一键，免确认）

右侧「部署」页签或完成态卡片上点「再部署」：前端调 `POST /api/deploy/runs/{id}/redeploy` → 后端新建 run、**复制冻结计划**、状态直接置 `confirmed` → 发起一轮 agent turn，系统注入「以下计划已由用户既往确认且签名一致，按计划直接执行」。AI 只做必要的现场复检（主机连通、目录现状），不再出计划、不挂起。

### 2.3 计划漂移

再部署前 AI 复检若发现项目变化必须改计划（如新增迁移步骤、端口/启动形态变化），不得自行改单执行：调 `deploy_plan` 提交新版本 → 签名变化 → 重新挂起确认。签名一致却试图提交不同计划的，后端按冲突拒绝并提示 AI 重新走确认。

### 2.4 失败、重试与跨会话续跑

- 任何步骤失败：`deploy_step(status=failed)`，AI 输出诊断后结束本轮（复用 pendingHalt 不发 done 的现有约定），卡片停在失败步并展开「诊断并修复后重试」。
- 重试：按钮向对话注入「继续刚才的部署」消息；AI 从账本读取冻结计划与各步状态，只重跑失败步及其后续。
- 跨会话：右侧「部署」页签对 `failed`/中断 run 提供「继续部署」，行为同重试；不重新规划、不丢失已完成步骤。

### 3.1 新增/修改组件

| `DeployStage` / `DeployStageTool` | 删除 | 固定枚举退役 |

| 确认负载 | 扩展 | PendingInteractionHub 增加 `deploy_plan` 类型（计划内容 + 可改字段） |

### 3.2 远程动作硬闸门（代码级，不靠提示词）

deploy_upload / deploy_extract_remote / deploy_start_remote / deploy_docker_remote 在 execute 入口校验：当前会话存在 run 且状态 ∈ {confirmed}，且该动作在计划步骤中能找到对应 kind。不满足时返回结构化错误：「计划尚未确认 / 该动作不在已确认计划内」。计划等待确认期间任何远程写操作都无法发生。

### 3.3 数据库变更（SQLite）

`deploy_runs` 表：

- 新增 `status TEXT NOT NULL DEFAULT 'confirmed'`（老记录默认值保证历史 run 可读）
- 新增 `plan_version INTEGER NOT NULL DEFAULT 0`
- 新增 `signature TEXT`
- 新增 `stack TEXT`
- `plan_json` 沿用，内容从字符串改为 1.2 的 JSON 结构
- `stages_json` 沿用列名，key 从固定阶段 id 改为计划 stepId

沿用既有 ALTER TABLE 增量迁移方式（Database.java 建表 + 补列逻辑）。老记录读取时：key 命中旧七阶段 id 时投影为只读固定步骤（后端保留一张旧 id → 中文标签的只读映射，仅供投影，不参与执行），不报错、不允许在老 run 上继续执行，只允许「再部署」（生成新结构 run）。

## 4. Docker 受控工具设计

`deploy_docker_remote`（EXECUTE 类，ChatService 自动批准名单与 upload/start 同级）：

入参：

- `host_key`、`appDir`（约定目录内）
- `mode`：`dockerfile` | `compose`
- dockerfile 模式：`image`、`containerName`（`[a-z0-9][a-z0-9_.-]{0,62}`）、`portMappings`（宿主端口/容器端口数字对，宿主端口 ≥1024）、`env`（`KEY=VALUE` 列表，白名单字符）、`restart`（`no`/`on-failure`/`always`/`unless-stopped`）
- compose 模式：`subcommand` 仅 `up -d` / `down` / `logs` / `ps`

硬约束：

- 沿用现有 shell 元字符黑名单（同 DeployStartRemoteTool 的 FORBIDDEN 正则）；
- 禁 `--privileged`、`--network=host`、任意 `-v` 挂载（v1 完全不放挂载；需要数据卷的场景由 generic.md 指引走 run_ssh 逐条确认）；
- 远程先探测 docker 存在性，缺失时返回大白话错误与安装建议，不自行安装；
- 执行与输出复用 SshJobManager，部署账本记录镜像名/容器名/compose 子命令。

## 5. 前端设计（frontend-v2）

### 5.1 移除

- 删除 `components/deploy/DeployStageCard.tsx/css` 及其在 ConversationPage composer 座的挂载。7 段进度条、X/7 计数、常驻 Dock 一并退出。

### 5.2 新增消息内卡：DeployPlanCard

在现有交互卡分发链路中按 `deploy_plan` 负载类型渲染，三态：

- **待确认**：栈徽标 + 计划标题 + 动态步骤清单（项目图标按 kind 映射，步骤数不固定）、产物/目录/端口 chips、端口与远程目录内联可编辑、「确认，开始部署」「取消」。黑白单色视觉契约，确认按钮 hover 才显底色。
- **执行中/失败**：步骤竖向导轨，状态点 pending/running（T 形扫光）/done/failed/skipped；运行步显示 purpose；失败步红色 summary + 「诊断并修复后重试」（turn 运行中禁用）；底部 chips 显示远程目录、产物、PID，docker 部署显示容器/镜像名。
- **历史只读**：随会话持久化回放，全部步骤折叠为完成态，无操作按钮（沿用现有历史交互卡只读约定）。

### 5.3 右侧「部署」页签

与终端/文件页签并列新增：

- 顶部列表：项目名 · 栈徽标 · 状态点 · 时间，跨会话拉取 `GET /api/deploy/runs`；
- 选中展开：步骤清单 + 元信息（同执行态卡片只读版）；
- 动作：failed/中断 run →「继续部署」；done run →「再部署」；
- 主机切换时列表不过滤（跨主机可见全部），但动作按钮在对应主机未连接时提示先连接（复用 HostConnectBlock 的连接引导）。

### 5.4 API 与状态

- `api/deployApi.ts`：类型从固定 7 键改为 `steps: Record<string, StepState>` + 计划结构；新增列表/redeploy 接口。
- 实时更新复用现有 serverStates / 交互回调通道，不新增 WebSocket。

## 6. 安全模型汇总

1. **工作区授权根不变**：本机命令仍锁 cwd，路径越界拒绝。
2. **三层闸门**：计划确认（远程写工具的代码级前置校验）→ 命令分级（构造安全工具自动放行 / run_ssh 走高危确认引擎 / Linux 高危命令硬拒绝）→ SSH 主机与 TOFU 不变。
3. **计划确认 ≠ 命令授权**：generic 步骤走 run_ssh 时逐条确认，不被计划确认覆盖；`SessionCommandGrants` 会话免确认仍只按精确命令匹配。
4. Docker 工具参数全部白名单校验，无自由文本命令通道。
5. 浏览器端不开放部署，本机能力仍走 Electron preload 最小授权面。

## 7. 实施切分（详细计划另出）

1. **批 1 账本与协议**：plan 结构化、状态机、签名、DB 迁移、DeployRunStore 改造、旧数据只读兼容。
2. **批 2 剧本与工具**：6 个 md、PlaybookService/Tool、DeployPlanTool（含确认挂起）、DeployStepTool，退役 DeployStage/Tool，总纲替换 7 步提示词，远程工具硬闸门。
3. **批 3 前端施工单**：删 Dock、DeployPlanCard 三态、交互分发接线、deployApi 改造。
4. **批 4 Docker + 兜底**：DeployDockerTool 白名单、generic 纪律联调。
5. **批 5 部署页签与续跑**：列表/详情/继续/再部署、redeploy 端点、跨会话续跑验证。

每批以 `mvn test` 全绿 + `npx tsc --noEmit` + `npm run build` 通过为交付门槛。

### 7.1 重点验收项

- 静态站只规划出 5 步（无 prepare），Java 项目规划出完整步，步骤数随项目变化、卡片无 7 的假设；
- 未确认计划前断网/强行触发，远程写工具零执行；
- 同计划再部署全程无确认打断；改端口后必须重新确认；
- 构建失败 → 关页面 → 次日「继续部署」从失败步恢复，已完成步不重跑；
