本文用于说明产品要解决什么问题、用户如何使用，以及结果如何验收。技术方案、开源组件及分阶段交付顺序另行确定。

## 1. 产品背景和目标

### 1.1 背景

用户有多个本地项目，典型项目包含 Java 后端、Vite 前端、数据库与 Redis，可能部署在一台或多台 Linux 服务器。每个项目的构建命令、部署位置、依赖服务、域名、进程状态和更新方法各不相同。

用户希望把这些信息交给 aya 长期管理：本地代码修改后，通过自然语言让 aya 完成构建和更新；打开应用时，能看到各项目与服务器的实际情况，并让 aya 协助处理环境和部署问题。

### 1.2 产品定位

aya 是一款桌面 AI 服务器管家，围绕“项目、服务器与部署实例”组织信息，协助用户准备环境、部署项目、持续更新、查看状态和处理故障。

目标使用者首先是产品创建者本人及具有类似需求的开发者。是否面向完全不具备开发经验的用户、团队协作或公开商业化，尚未决定。

### 1.3 核心目标

1. 让 aya 逐步了解项目的组成、依赖和部署方式，并能按实际检查更新资料。
2. 让用户通过项目和服务器两个入口查看同一组关系与状态。
3. 让用户在本地改完代码后，用自然语言发起可追踪的构建、部署和验证。
4. 支持同一项目跨服务器部署、同一组件的多个实例，以及多项目共享基础设施。
5. 为指定 Git 分支提供可选的自动发布能力，并与手动更新共用发布流程。
6. 对部署错误进行可控修复：构建脚本、依赖和部署配置可自动调整；业务逻辑或功能修改必须先得到用户确认。
7. 使用可靠、可复核的执行和检查结果展示部署状态，减少用户反复查看命令日志的负担。

## 2. 已确认的边界

### 2.1 使用与运行

- aya 是独立新项目；旧 aye-aye 是需求、代码和设计参考之一，不设迁移旧项目或旧数据的目标。
- aya 在桌面应用运行期间接收指令、检查状态和执行部署。用户不要求关闭桌面之后继续监控或触发自动发布。
- 已部署到服务器的业务应用独立运行，不依赖 aya 桌面保持打开。
- 再次打开 aya 后，需要核对服务器和应用的实际情况，并显示最后检查时间。连接失败或未检查时，状态应为“未知”等明确状态，不能沿用旧的正常状态。
- 部署执行中关闭桌面时，远端任务如何处理、能否继续以及是否自动恢复，尚未确定；重新打开后的实际状态核对属于目标能力。

### 2.2 项目与环境

- 典型目标项目包括 Java 后端、Vite 前端、数据库、Redis。
- aya 需要具备按项目和服务器情况准备、安装及配置 Java、Nginx、数据库和 Redis 等环境的能力。具体支持版本、Linux 发行版和已有环境兼容范围待定义与验证。
- 支持同一个 Java 后端部署到两台服务器，由 Nginx 分发请求；也支持前后端或不同组件分别部署。
- 项目与服务器是多对多关系，不预设固定数量；可支持的性能规模需要实际测试，当前不做无限规模承诺。
- 原生进程、容器或两者共存等部署方式尚未决定。

### 2.3 修改与验证

- 为完成已发起的部署，可以自动修复构建脚本、依赖和部署配置。
- 涉及业务逻辑或功能的修改，必须先取得用户确认；判断应考虑实际影响，包括通过命令、脚本或依赖调整间接造成的业务变化。
- 发布过程中的构建结果、启动状态和适用的健康检查，需要自动验证并留存证据。
- 人工业务验收功能先预留，是否实现及具体交互后续决定；它与修改业务逻辑前的确认是不同事项。
- 已运行应用故障的自动修复范围尚未确定，本次部署失败可自动修复的授权不自动扩展为所有线上故障都可以自行修改。

## 3. 产品概念

| 概念 | 含义 | 需要记录的主要信息 |
| --- | --- | --- |
| 项目 | 用户管理的一个业务或应用，可关联本地源码 | 名称、源码位置、组件、依赖、部署方案、发布记录 |
| 环境 | 同一项目不同的运行目标，例如测试或生产 | 环境名称、关联组件、目标服务器、配置范围；是否在首版提供完整多环境能力待定 |
| 组件 | 构成项目的可部署或可依赖部分 | 例如前端、Java 后端；构建方式、配置、依赖与实例 |
| 部署实例 | 某个组件在具体目标上的一个运行实例 | 所属项目与组件、服务器、版本、运行状态、检查时间和日志位置 |
| 服务器 | 项目或共享服务的运行目标 | 连接方式、状态、安装的环境、关联项目、资源与端口信息 |
| 共享服务 | 多个项目可能共同使用的基础服务 | 例如 Nginx、数据库、Redis；所在服务器、管理归属、依赖项目和状态 |
| 发布任务 | 一次由用户指令或 Git 更新触发的执行 | 来源、目标、各阶段结果、产物、各实例结果、日志与时间 |

项目页和服务器页应从同一组关系生成：从项目能看到所用服务器，从服务器也能看到相关项目。组件、实例和共享服务的具体持久化结构由技术方案确定。

## 4. 用户场景

### 场景 A：首次接管项目并部署

1. 用户选择本地项目，添加或选择目标服务器。
2. aya 读取项目文件并检查服务器，识别前端、后端、构建方式及可识别的依赖。
3. aya 形成项目档案与部署方案，根据项目和服务器现状准备所需环境。
4. aya 构建、上传、启动并检查结果，展示项目访问方式、部署实例和任务记录。
5. 遇到需要修改业务逻辑的情况，aya 说明拟修改内容并等待确认。

自动识别的覆盖范围、初次方案的确认方式与安装流程细节待设计。无法识别时应清楚说明缺少的信息，不能虚构检查结果。

### 场景 B：本地代码更新

1. 用户在本地修改代码，对 aya 说“更新这个项目”。
2. aya 以用户选择的当前本地代码为来源，未提交到 Git 的修改也可纳入本次发布。
3. aya 记录可追溯的本次来源或产物标识，复用项目部署方案执行构建与发布。
4. 界面显示各阶段、各目标实例的结果以及最终自动检查证据。

本地快照的实现形式、包含和排除文件的规则待设计；不得只记录 Git 提交而遗漏本次选择发布的未提交修改。

### 场景 C：一个后端双节点

1. 用户将同一 Java 后端关联到服务器 A 和服务器 B，并通过 Nginx 分发请求。
2. 项目页分别显示两个实例对应的服务器、版本、检查状态及最近检查时间。
3. 一次发布中，如 A 成功而 B 失败，aya 分别展示实际结果，整体任务不能显示为全部成功。
4. 服务器页可反向查看各服务器上的实例和关联项目。

发布顺序、流量切换、零停机与自动回滚策略尚未确定，不能在当前阶段承诺。

### 场景 D：多个项目共享服务器或服务

1. 项目 A 和项目 B 可以部署到同一台服务器，也可以共同使用 Nginx、数据库或 Redis。
2. 项目页显示该项目使用的服务；服务器页显示该服务及其关联项目。
3. aya 检查端口、域名和共享服务时，应呈现已知占用与关联影响，避免把一个项目的状态误记为另一个项目的状态。

### 场景 E：指定分支自动发布

1. 用户可为项目配置 Git 来源和指定分支，选择启用自动发布。
2. aya 运行期间检测到指定分支的新版本时，以明确的 Git 提交作为来源创建发布任务。
3. 自动发布与本地手动更新共用执行流程和发布记录；同一项目环境的发布任务应按顺序处理，避免相互覆盖。

关闭桌面期间不要求触发发布；重新打开后是否补跑、检测频率与去重规则待设计。

### 场景 F：部署失败与修复

1. 构建或部署失败时，aya 展示失败阶段、目标、关键错误及已有执行记录。
2. aya 可在授权范围内自动修复构建脚本、依赖或部署配置，重新验证并记录修改和结果。
3. 若预计需要改变业务逻辑或功能，aya 展示拟修改内容并等待用户明确确认。
4. 用户拒绝或尚未确认时，不执行该业务修改；如果后续部署依赖这项修改，应说明未完成原因，不能报告已成功。

## 5. 功能需求

本节描述目标能力；是否全部纳入首次发布、具体交付顺序和细节仍待确认。

### 5.1 项目接入和项目记忆

| 编号 | 需求 | 验收关注点 |
| --- | --- | --- |
| FR-01 | 添加和选择本地项目，保存项目身份与源码位置 | 重新打开后可找到已有项目；目录不可用时有明确提示 |
| FR-02 | 识别项目组件、构建方式与依赖，并建立可查看的项目档案 | 有证据来源或检查结果；不能把模型猜测直接展示为已确认事实 |
| FR-03 | 记录和更新服务器、组件、实例、共享服务及部署关系 | 多项目、多服务器可双向查询，关系变化后两个视角一致 |
| FR-04 | 记录经过验证的构建和部署方案，供后续任务复用 | 能查看历史方案及最近执行结果；变更时有记录 |
| FR-05 | 读取项目状态时同步核对实际情况 | 标注检查时间；未连接或未检查显示未知 |

### 5.2 服务器与环境

| 编号 | 需求 | 验收关注点 |
| --- | --- | --- |
| FR-06 | 添加服务器并建立连接，展示连接及检查状态 | 连接失败有原因；不把无法连接认作服务正常 |
| FR-07 | 检查和准备项目需要的运行环境 | 显示已识别环境、准备步骤与结果；实际支持范围待定义 |
| FR-08 | 支持安装和配置 Java、Nginx、数据库和 Redis 等目标环境 | 能区分已有环境、执行结果和失败原因；具体版本与方式待定 |
| FR-09 | 展示服务器上的项目、实例、共享服务与已知资源占用 | 与项目视角对应同一组关系；共享服务能查到关联项目 |

### 5.3 发布与持续部署

| 编号 | 需求 | 验收关注点 |
| --- | --- | --- |
| FR-10 | 接收自然语言指令，基于当前本地代码更新项目 | 可纳入未提交修改；记录本次来源或产物标识 |
| FR-11 | 对项目启用指定 Git 分支的自动发布 | aya 运行期间按配置触发；记录实际提交及触发来源 |
| FR-12 | 两种触发方式共用构建、发布、验证与记录流程 | 发布历史能区分触发来源，结果模型一致 |
| FR-13 | 跟踪组件及多服务器部署实例的独立结果 | 显示每个实例的目标、版本、执行结果和检查时间 |
| FR-14 | 保存任务日志、关键步骤、产物和结果 | 用户能定位失败阶段及相关目标；展示实际证据 |
| FR-15 | 处理同一项目环境的并发发布 | 发布按顺序处理，避免互相覆盖；排队与去重细节待设计 |
| FR-16 | 支持停止任务，并呈现停止后的已完成与未完成部分 | 不把停止理解为已撤销已完成的远程操作；具体中断与恢复行为待设计 |

### 5.4 AI 协作与修复

| 编号 | 需求 | 验收关注点 |
| --- | --- | --- |
| FR-17 | aya 能读取项目和服务器资料，执行适合当前任务的工具 | 展示关键执行动作、结果和错误；可追踪任务上下文 |
| FR-18 | 部署失败时允许自动修复构建脚本、依赖与部署配置 | 保存修改与重新验证结果；不扩展为未经确认的业务功能修改 |
| FR-19 | 修改业务逻辑或功能前必须得到用户确认 | 包含直接编辑、命令或脚本间接引起的业务变化；拒绝或未确认时不得执行对应修改 |
| FR-20 | 用户可查看并回应 aya 的问题或业务修改确认 | 等待状态清楚；用户拒绝时说明对当前任务的影响 |
| FR-21 | 提供任务进行中的状态、结果与必要的上下文 | 切换视角后能够找到项目关联任务；具体页面布局待设计 |

权限实现不能只依赖模型的自我判断或某一个编辑工具的提示词；对于无法确定是否会改变业务行为的操作，应在执行前澄清其影响并处理用户确认。具体控制与验证机制待技术设计。

### 5.5 状态与验证

| 编号 | 需求 | 验收关注点 |
| --- | --- | --- |
| FR-22 | 通过实际构建、启动和适用的健康检查判断结果 | 结果有工具或检查证据，不能仅以 AI 声明“成功”为依据 |
| FR-23 | 区分正常、异常、未知、检查中等状态 | 未检查、无法连接或数据过期不能误报正常；未知不自动等同失败 |
| FR-24 | 发布部分成功时展示各实例及整体任务结果 | 存在失败或未核实实例时，不能声称全部实例发布成功 |
| FR-25 | 保存检查时间、失败原因与关键证据 | 重新打开后能区分历史记录和本次检查结果 |
| FR-26 | 为人工业务验收预留扩展能力 | 是否实施、界面及是否阻塞发布待定；自动工程检查仍保留 |

## 6. 主要界面与交互建议

以下信息架构为讨论中提出的建议，视觉形式和交互细节待设计。

### 6.1 项目

- 项目列表：名称、关联环境或服务器、最近发布、最近检查状态。
- 项目详情：源码与组件、实例、服务器、依赖服务、访问方式、发布历史和相关任务。
- 常用操作：向 aya 描述任务、更新项目、检查状态、查看记录。

### 6.2 服务器

- 服务器列表：连接状态、最近检查时间和关联项目概况。
- 服务器详情：关联项目、实例、共享服务、已知端口与资源情况。
- 从服务器或服务可返回查看对应项目和任务。

### 6.3 任务

- 查看环境准备、构建、部署、修复和检查的执行记录。
- 展示当前步骤、目标服务器、关键输出、错误、等待确认状态与实例结果。
- 支持停止、补充要求以及回应需要确认的业务修改；具体交互和运行中关闭桌面的行为待设计。

## 7. 发布状态建议

下面是为避免界面误报而提出的状态模型建议，具体字段与术语后续确认。

| 对象 | 建议状态 | 说明 |
| --- | --- | --- |
| 任务 | 排队中、运行中、等待用户、成功、失败、已停止、结果待核对 | 整体结果应结合实际步骤与实例结果 |
| 实例 | 检查中、正常、异常、未知 | 未连接、未检查、过期信息均不能显示为当前正常 |
| 实例发布结果 | 未开始、进行中、成功、失败、未核实 | 每个目标分别记录；部分成功不等于整体成功 |

“自动检查通过”表示所配置的工程检查通过；它不自动代表所有业务功能已被人工验收。

## 8. 产品与数据要求

- **结果可追溯**：任务应能关联项目、来源、目标服务器、执行步骤、实例结果、检查时间和关键证据。
- **状态有时间语义**：展示最近检查时间；无法获取当前状态时标记未知，不伪造实时性。
- **异常可理解**：优先显示失败阶段、影响范围和可以继续处理的事项，详细日志按需查看。
- **操作与数据边界清楚**：服务器凭据、模型密钥和项目资料需要合理保存；发送给模型的数据范围应可说明。具体存储、脱敏和授权机制待技术设计。
- **可持续维护**：技术选型应适合用户掌握的 JavaScript/TypeScript，优先评估可复用的开源组件；具体框架与模块边界待验证。
- **性能目标待定**：不在缺少测试数据时承诺项目数、服务器数、响应时间或可用率上限。

## 9. 验收场景

以下是目标级验收场景，不表示已实现，也不自动等于首版交付范围。

1. **接管项目**：选择含 Java 后端、Vite 前端和数据库/Redis 依赖的示例项目与服务器，形成可检查的项目组件、依赖和部署关系；识别失败的部分明确显示。
2. **共享资源**：两个项目共用服务器和数据库/Redis，从任一项目页和服务器页都能查到一致的关联；无法检查的服务显示未知及检查时间。
3. **双节点**：同一 Java 组件存在两个服务器实例，分别展示版本和状态；一个实例发布失败时，整体不显示全部成功。
4. **本地更新**：未提交的本地修改被纳入用户选择的发布来源；任务记录可追溯来源或产物，并包含各阶段与实例结果。
5. **Git 发布**：应用运行期间指定分支发生更新后，按已启用配置产生任务，记录实际提交；与手动任务使用同一套发布结果模型。
6. **权限边界**：模拟需要修复构建配置时可自动处理并留痕；需要修改业务功能时等待确认，拒绝后不发生该修改。测试应覆盖直接编辑与间接执行路径。
7. **真实结果**：构建、上传、启动或探活任一步失败时，页面显示对应事实；仅有 AI 的完成声明不能使发布显示成功。
8. **重新打开**：关闭桌面后服务器业务应用仍可独立运行；再次打开 aya 后核对实际状态，无法连接的服务器显示未知而非旧的正常状态。

## 10. 建议的推进顺序

这是调研和验证顺序的建议，不是已经确定的首版范围，也不删除双节点、多服务器或 Git 自动发布目标。

1. 根据本文细化首次接入、项目/服务器双视角、发布与确认的交互。
2. 评估可复用的 Agent、SSH、终端与本地存储组件，验证与目标桌面环境的兼容性。
3. 用代表性的 Java + Vite 项目验证项目识别、环境准备、本地更新、自动检查和记录。
4. 验证共享资源、多服务器与双实例发布，以及部分失败时的状态展示。
5. 完善指定 Git 分支自动触发和其他部署方式，并根据实际项目继续调整。

技术候选和已完成的离线最小验证见 [开源组件调研](./2026-10-27-aya-开源组件调研.md)。

## 11. 待讨论与待设计事项

1. **部署方式**：现有项目采用原生进程、Docker，还是不同项目各不相同；相应环境如何准备与隔离。
2. **首次接管**：项目结构和服务器环境不完整时，用户希望如何补充信息；方案和环境准备的交互如何组织。
3. **双节点发布**：实例更新顺序、流量切换、连续可用性的目标和失败时处理方式。
4. **数据库变更**：结构迁移、版本兼容、备份和失败恢复如何与发布任务配合。
5. **故障处置**：已运行项目异常时，自动诊断、通知、自动修复分别涵盖哪些情况。
6. **桌面退出**：部署进行中退出时的任务状态、远端执行、重新打开后的核对和恢复方式。
7. **Git 自动触发**：检测频率、去重、失败重试和桌面关闭期间变更是否补跑。
8. **人工业务验收**：是否实现、如何记录以及是否影响发布流程。
9. **数据与性能**：版本、日志、任务记录的保留策略，以及需要支持的实际性能指标。
10. **工程选型**：独立新项目的存放位置、桌面框架、Agent 内核、数据库及开源组件；实际复用内容的许可与第三方声明。
