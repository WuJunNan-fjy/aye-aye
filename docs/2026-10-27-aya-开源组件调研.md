# 新 aya 的开源组件调研

日期：2026-10-27  
状态：初步调研与离线最小验证，尚未决定最终选型

新 aya 是独立项目。现有 aye-aye、ZCode、deepseek-harness、本地 Agent 源码和 GitHub 项目可作为直接依赖、代码复用或设计参考的来源。具体代码在引入前核对对应版本的许可证、版权声明与第三方依赖。

## 1. Agent 核心

| 候选 | 初步判断 | 适配价值与待核实事项 |
| --- | --- | --- |
| [Pi Agent Core](https://github.com/earendil-works/pi/tree/main/packages/agent) | **优先做接入原型** | MIT，TypeScript/Node 的 Agent 循环、工具调用、流式事件、中途输入与取消。工具前置钩子可用于接入 aya 的权限判断。业务修改确认、统一工具约束、会话持久化及执行审计仍需自己设计和验证。 |
| [Pi Coding Agent SDK](https://github.com/earendil-works/pi/tree/main/packages/coding-agent) | **与 Core 做接入对比** | 包含自定义工具、会话和文件操作，能力更完整；本地版本默认启用部分通用工具并加载资源，接入时需要明确控制工具和资源，不能直接认为满足 aya 的业务修改确认规则。 |
| [Pi Web](https://github.com/agegr/pi-web) | **重点研究局部代码与交互** | 本地源码是 MIT，实际通过 SDK 在进程内创建会话、订阅事件；可研究会话与流式工具展示。其 Next.js Web 应用结构需评估是否适合 Electron。 |
| [OpenCode](https://github.com/anomalyco/opencode) | **研究并比较 SDK 方案** | 本地仓库为 MIT，代码以 TypeScript/Bun workspace 为主。传统 SDK 会启动独立进程；本地另有进程内 `sdk-next`，但标记 private 且依赖 workspace，独立使用及打包需验证。 |
| [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) | **研究会话和工具流水线，按需复用** | MIT，TypeScript/Node。事件驱动的会话、工具审批和恢复机制值得研究；整体平台的插件与依赖较多，按需评估实际引入成本。 |
| [ZCode](https://github.com/zai-org/ZCode) | **研究运行时、桌面交互及模型适配** | 第一方代码为 Apache-2.0。实际复用具体代码或资源时，检查该仓库的 NOTICE 和第三方来源声明。 |
| 本地 DeepWork | **待核实权属后评估** | `packages/ai` 提供 TypeScript Agent Loop 和工具注册，但依赖 workspace 包；抽查的统一工具执行路径未接入其权限引擎，会话持久化默认实现为空。根目录未发现许可证文件，复制或分发前需核实权属与条件。 |
| 本地 Claude Code 源码目录 | **来源与许可待核实** | 本次未发现根许可证或根 README；不能根据目录名称推断分发授权。 |

本地 Pi 源码抽查的包为 `@earendil-works/pi-agent-core` 0.82.1，声明 Node >=22.19.0；源代码和线上仓库可能更新，正式采用时应锁定并复核实际版本。

### Pi 的离线最小验证

在当前机器使用本地已存在的 Pi 编译产物和 Node v22.22.2，以模拟模型响应与模拟工具运行一次 Agent 回合。验证结果：工具前置钩子被调用一次，阻断后工具执行次数为零，Agent 继续接收模拟模型的后续回复并结束。

该验证未连接模型或服务器、未执行文件修改，也未验证 Electron 打包、真实模型、会话恢复或完整权限系统。Pi 的钩子提供的是拦截点；识别“改构建配置”与“改业务行为”、覆盖命令间接修改等能力仍需要新项目实现并验证。

本地证据：`E:\Agent的工作目录\Agent的工作目录\1-pi 源码\packages\agent\src\agent-loop.ts` 的 `prepareToolCall`；`E:\Agent的工作目录\Agent的工作目录\1-pi-web 源码\lib\rpc-manager.ts` 的 SDK 会话创建路径。

## 2. 远程连接和桌面能力

| 候选 | 类型 | 初步判断 |
| --- | --- | --- |
| [ssh2](https://github.com/mscdex/ssh2) | MIT，Node.js SSH/SFTP 库 | 可作为远程命令、交互 shell、文件传输的直接依赖候选。仍需封装连接生命周期、取消、任务记录与错误处理。默认不设置 `hostVerifier` 时自动接受主机密钥，需接入指纹验证。 |
| [xterm.js](https://github.com/xtermjs/xterm.js) | MIT，终端前端组件 | 可作为交互式终端显示候选；与 SSH 后端配合，负责显示和输入。 |
| [node-pty](https://github.com/microsoft/node-pty) | MIT，本地伪终端模块 | 如需要桌面内本地交互终端可评估；包含原生模块，需要验证 Windows 与 Electron 打包。 |
| [better-sqlite3](https://github.com/WiseLibs/better-sqlite3) | MIT，Node.js SQLite 绑定 | 可评估作为本地项目、服务器和发布记录存储；含原生模块，需要验证所选 Electron 版本和安装包。 |
| [simple-git](https://github.com/simple-git-js/simple-git) | Node.js Git 包装 | 可评估本地 Git 状态、提交与分支检测；是否作为依赖及实际选用版本的许可、打包方式待核实。 |

这些库分别解决底层连接、显示或存储；项目/服务器多对多关系、部署实例、发布状态及共享资源依赖仍需要 aya 自己建立。

## 4. 初步方案与验证顺序

1. **新建独立 TypeScript 项目**：保留桌面 UI 与本地运行时的职责边界，新项目存放位置和具体框架待定。
2. **Agent 原型**：优先比较 Pi Agent Core 与 Pi Coding Agent SDK；接入项目自有工具、业务修改确认与会话记录，验证真实模型和中途取消。
3. **连接原型**：评估 ssh2 的认证、主机指纹、SFTP、长任务、断连与 Electron 打包；无需将开源部署平台整套作为前置条件。
4. **产品专有能力**：设计项目—组件—部署实例—服务器与共享资源的关系，记录构建来源、发布过程、实例结果及健康检查证据。
5. **发布原型**：选择一个有代表性的 Java + Vite 项目，先在隔离测试服务器验证实际环境准备、构建、发布和结果检查；双节点、Git 自动触发及多种部署方式在原型后继续验证。

这些顺序是技术调研建议，不意味着将产品功能限制为单机或固定数量服务器，也不代表已经确定只支持某一种部署方式。
