# TermMind 桌面端生产级升级方案

> 日期：2026-09-28
> 范围：`apps/termmind-desktop`（Electron 外壳）+ `apps/termmind-server`（Java/Spring Boot sidecar）的桌面打包与运行体系
> 参照对象：E 盘 DeepSeek 桌面端项目 `e:\ideaCode\me\deepseek-harness-desktop`（核心为 `dsh-desktop-next`，生产级 Electron + 本地后端架构）

---

## 1. 关键发现：Java 版打包链路目前是"断"的

`apps/termmind-desktop/electron-builder.yml` 声明把 `build/backend` 打进安装包，但：

- `build/backend` 在仓库中**不存在**（`.gitignore` 忽略了 `build/backend/` 与 `build/jre/`）；
- 全仓库**没有任何脚本**负责：执行 `mvn package`、把 jar 复制为 `server.jar`、准备内置 JRE；
- README 只写了目标布局（`resources/backend/server.jar`、`resources/backend/runtime/bin/java.exe`），未落地。

实证：E 盘已安装的 `E:\TermMind\resources\backend` 内仍是**旧版 Node 后端**（`dist/main.js`、`mastra-agent.service.js` + `node/node.exe`），不是 Java jar。

结论：

- 开发时能运行，是因为 `src/main/index.ts` 回退到 Maven `target/` 找 jar、并回退使用系统 JDK 17；
- **一台未安装 JDK 的普通用户机器，用当前配置打出的包无法启动**；extraResources 源目录缺失还会导致打包行为异常。

这是升级的第一优先级事项。

## 3. 与 DSH Desktop（dsh-desktop-next）的差距

### 3.1 后端进程管理：一次性启动 vs 完整状态机

现状：spawn → 正则抓取 stdout 端口 → 30s 超时。**启动成功后** Java 进程崩溃、被杀毒软件杀掉或 OOM，前端无感知，仅表现为接口全部报错。

DSH 做法（`src/backend-controller.ts`、`src/host-process.ts`）：

- 显式状态机 `starting / ready / error`，状态推送到 UI，错误页保留原始堆栈（`startup-error.ts`）；
- 并发启动去重；stop 可取消进行中的启动；cleanup 失败用 `AggregateError` 聚合；
- 运行中子进程 fatal 同样上报告警；
- 分级关停：shutdown 信号等待 10s → SIGTERM 等待 5s → SIGKILL 等待 5s；
- stderr 保留 64KB 环形缓冲用于诊断；
- 所有子进程 IPC 消息做结构化校验。

### 3.2 单实例锁

现状：**无** `requestSingleInstanceLock`。重复双击图标会产生多个 JVM、多个后端争抢同一个 SQLite 文件（写锁冲突、分片上传状态错乱）。

DSH（`src/single-instance.ts`）：启动即抢锁，二次启动仅唤起/聚焦已有窗口，并兼容安装器退出请求。

### 3.3 启动体验：JVM 冷启动期"看起来没反应"

现状：`createWindow` 中 **await 后端启动之后才创建窗口**。Electron 窗口本可秒开，但 Spring Boot 冷启动约 3~8 秒，期间屏幕无任何反馈，用户会反复双击（叠加无单实例锁问题会真的开多实例）。

生产级做法：立即显示启动闪屏（logo + loading），后端 ready 后再加载主 UI；后端状态在界面可见。

### 3.4 崩溃恢复 / 安全模式 / 诊断

| DSH 模块 | 作用 | TermMind 现状 |
| --- | --- | --- |
| `recovery.ts` | 关键配置快照（SHA256 校验、原子恢复）、出厂重置前备份 | 无 |
| `safe-mode.ts` | 启动失败时以隔离数据目录进入安全模式 | 无 |
| `diagnostics.ts` | 分级日志落盘、`maskSecrets` 脱敏、一键导出诊断包 | 后端日志仅 console，不落盘、不轮转 |
| `startup-error.ts` | 结构化启动失败错误页 | 仅 reject，用户无感知 |

实际风险场景：SQLite 文件损坏（异常断电、强杀进程）时无备份与修复入口。

### 3.5 自动更新

现状：已安装 `electron-updater` 依赖但**零调用**。

DSH（`updates.ts` / `update-installer.ts` / `update-state.ts`）：完整状态机（checking/downloading/ready/installing/error）、独立更新缓存目录；安装前先 lock/drain 后端任务，确认优雅退出后才允许安装。

### 3.6 打包工程化、签名与安全

- DSH 配置 **Electron Fuses** 并由 `scripts/verify-fuses.ts` 在打包后**实际启动产物 exe 做 smoke test**；
- Windows 代码签名；macOS `hardenedRuntime` + entitlements + **公证（notarize）**；
- GitHub Actions CI：typecheck + 主机层单测 + Playwright 验证 + 发布流水线；
- TermMind：无 Fuses、无签名、无 CI、无产物校验。未签名 + spawn java.exe + 随机端口本地 HTTP 是杀软误报率最高的组合，且会触发 SmartScreen。

### 3.7 其他产品级能力

托盘图标（关窗不退后端 / 最小化到托盘）、系统通知、可迁移数据目录（`data-directory.ts`）、统一退出协调（SIGINT/SIGTERM/before-quit/window-all-closed，见 `shutdown.ts`）、deep link —— 均缺失。

## 4. Java sidecar 的专属问题（与 Node sidecar 的不同）

### 4.1 JRE 必须随包，jlink 裁剪有讲究

不能要求用户安装 JDK。用 jlink 裁剪运行时（目标约 45~60MB，完整 JRE 约 180MB）：

```bash
jlink --add-modles java.base,java.sql,java.naming,java.desktop,java.management,java.net.http,jdk.crypto.ec,jdk.unsupported \
  --strip-debug --compress=zip-9 --no-header-files --no-man-pages \
  --output runtime
```

注意：

- **必须包含 `jdk.crypto.ec`**，否则 HTTPS 连 DeepSeek API 握手失败；
- 用 `jdeps --print-module-deps` 分析 fat jar 校正模块清单，不凭感觉；
- sqlite-jdbc 原生库从 jar 内自动解压加载，需保证临时目录可写（Program Files 下不可写，指定 `-Dorg.sqlite.tmpdir` 到 userData 下）。

目标布局（jar 与运行时分离，路径约定只保留一种）：

```text
resources/
  app.asar
  backend/server.jar
  runtime/bin/java.exe (+ lib/...)
```

### 4.2 就绪信号：替换日志正则为结构化握手

现状靠正则匹配 stdout 的 `running on http://127.0.0.1:(\d+)`，受日志缓冲、格式变更、第三方库相似输出影响。

改为：Spring 侧（`TermMindApplication`）输出**固定前缀单行 JSON**：

```text
TERMMIND_READY {"port":54321,"pid":12348,"version":"0.0.1"}
```

Electron 按行解析 JSON；随后轮询 `/api/health` 确认真实就绪并做运行期心跳。Token 不进日志，仍走环境变量。

### 4.3 Windows 没有真正的 SIGTERM：优雅关停需专门设计

Windows 上 Node 对子进程 `kill('SIGTERM')` 实为 TerminateProcess 硬杀，Spring shutdown hook 不执行，导致 SQLite WAL 不 checkpoint、SSH 通道/SSE/分片上传被硬切断。

方案：

1. 后端提供 token 鉴权内部端点 `POST /api/internal/shutdown`，配合 `server.shutdown=graceful` 与超时；
2. Electron 退出时先调该端点，等待进程退出/端口释放（约 10s）；
3. 超时再 `taskkill /PID xxx /T /F` 强杀进程树；
4. 写 PID 文件辅助识别与清理。

### 4.4 jar 文件锁导致 NSIS 升级失败（经典 Java 桌面坑）

安装在 Program Files 下时，运行中的 `resources/backend/server.jar` 与 JRE 文件被 java.exe 锁定。NSIS 只保证 TermMind.exe 退出，**孤儿 java.exe 会导致覆盖安装报"文件被占用"**。

要求：

- `before-quit` 中 100% 等待 Java 子进程结束；
- NSIS 脚本（`installer.nsh`）加保险：安装前检测并清理残留 java 进程/PID 文件；
- electron-updater 的 `quitAndInstall` 前必须走完同一关停闸门。

### 4.5 JVM 冷启动优化

- **AppCDS**：发布前训练一次类数据共享归档（`.jsa`）随包，启动通常快 20%~40%（Spring Boot 3.3+ 内置 CDS 支持）；
- 固定参数：`-Dfile.encoding=UTF-8`、`-Dstdout.encoding=UTF-8`（项目有中文文件名乱码历史，必须加）、合理的 `-XX:MaxRAMPercentage` / `-XX:MaxMetaspaceSize`；
- 精简无用自动配置、降低启动日志级别；
- Windows 管道默认 GBK，spawn 侧显式保证 UTF-8，避免握手行与中文日志乱码。

### 4.6 崩溃诊断

配置 `-XX:ErrorFile=<userData>/logs/hs_err_%p.log` 输出 JVM crash 文件；Electron 按退出码区分提示文案（1=应用异常，展示日志导出；143=被杀，提示杀软/手动终止等）。

### 4.7 包体与跨平台

- 预估体积：Electron ~180MB + JRE ~55MB + fat jar ~40MB；NSIS LZMA 压缩后安装包约 90~130MB，属正常水平；
- macOS 的 jlink runtime 必须在 macOS 上生成，并对 runtime 内所有可执行文件逐个 codesign，再公证；arm64/x64 分别构建；
- electron-updater 差分块只对 asar 有效，jar/JRE 在 extraResources 中变化会整块重下——JRE 保持稳定、固定目录即可。

## 5. 升级路线（按优先级）

### P0：不做就不能称为桌面产品

1. **补齐打包链路**：新增 `scripts/prepare-backend`：`mvn package` → jar 复制为 `build/backend/server.jar`；缓存下载 Temurin 17 → jdeps + jlink 生成 `build/runtime`（先 Windows，后 mac/linux）；接入 `npm run dist`。
2. **启动闪屏窗口**：立即显示（沿用 T 形 logo loading 动画与黑白视觉契约），后端 ready 后切换主 UI。
3. **单实例锁**：`requestSingleInstanceLock` + 二次启动聚焦窗口。
4. **结构化握手 + 健康心跳 + 崩溃感知**：JSON 行握手替换正则；`/api/health` 心跳；运行中崩溃检测与自动重启；前端显示后端状态条。
5. **优雅关停**：内部 shutdown 端点 + 分级关停 + 强杀进程树 + PID 文件；NSIS 安装前残留进程清理（解决 jar 锁）。
6. **产物 smoke 校验**：afterAllArtifactBuild 实际启动产物 exe 探测 health（参照 DSH verify-fuses 思路）。

### P1：可分发、可维护

7. **Electron Fuses 硬化**（`@electron/fuses`：禁 RunAsNode、仅从 asar 加载等）。
8. **electron-updater 接线**：先用 GitHub Releases generic feed；安装前走优雅退出闸门。
9. **日志与诊断**：日志落盘 `userData/logs`（按大小轮转、脱敏、一键导出）+ JVM crash 文件收集。
10. **代码签名/公证**：预算有限至少先签 Windows，降低 SmartScreen 与杀软误报。
11. **数据安全**：SQLite 启动时自动备份（保留最近 N 份）+ 损坏后的恢复/安全模式入口。
12. **CI**：GitHub Actions：mvn test → tsc → 打包 → smoke → 发布。

### P2：体验打磨

13. AppCDS + JVM 参数精调，量化冷启动耗时；jlink 模块精修瘦身。
14. 托盘图标（明确关窗策略：最小化到托盘 vs 退出停后端）、系统通知。
15. macOS arm64/x64、Linux AppImage 产物矩阵。
16. 可自定义数据目录与迁移（参照 `data-directory.ts`）。

## 6. 总结

当前 Electron 外壳的安全设计在线，但本质仍是"开发时方便联调 Java 的壳"：后端生命周期只覆盖启动、缺失出包流水线、无单实例与更新体系。对照 DSH Desktop 最应借鉴的是四项能力——**后端状态机与崩溃感知、单实例/优雅退出、打包后校验与签名更新、诊断恢复体系**。

Java 相对 Node 额外要解决四个专属问题：

1. JRE 随包（jlink，含 `jdk.crypto.ec`）；
2. JVM 冷启动期的启动反馈；
3. Windows 无 SIGTERM 下的优雅关停；
4. jar 文件锁导致的安装/更新失败。

建议立即动手的前两件事：**补齐 jar + JRE 的自动打包链路**、**防止孤儿 java.exe 锁文件（单实例 + 优雅关停 + NSIS 清理）**。
