# 小白一键部署设计（工作区 + AI 打包 + 上传 + 远程启动）

日期：2026-09-20
状态：设计已按方案 C 展开，待用户评审，未进入实现

## 0. 目标与范围

### 0.1 要解决的问题

不懂代码的小白用户拿到一个陌生项目（Git 地址或本地目录），希望在 TermMind 里完成：

```
选项目 → AI 看懂项目 → 准备本机环境 → 构建打包 → 确认产物
→ 上传到服务器 → 远程启动并验证
```

全程在对话中完成，每一步有小白能看懂的进度卡片；危险操作才打断用户确认。

### 0.2 明确做

1. 工作区：选择本地目录（原生对话框）/ 从 Git 地址 clone，持久化登记，工作区是唯一授权根。
2. 本机执行：在工作区内执行命令（环境检查、install、build），支持长命令异步执行与有界输出。
3. 部署阶段账本：7 个阶段的状态、命令、输出摘要、产物、远程路径全部落库，失败可单步重试、重开页面可恢复。
4. 直传：后端内部把本地产物以流式 SFTP 推到目标主机（内存恒定，GB 级包可用）。
5. 远程启动：解压、运行时检查、nohup 启动、pid/日志管理、探活并回显访问地址。
6. 审批分级：安全命令自动执行；高危命令硬拒绝；其余命令弹窗（大白话解释用途与风险）；支持「本会话相同操作不再询问」。

### 0.3 明确不做（第一刀）

- 不做 Docker / docker-compose 部署、不写 systemd service（第二刀视使用情况再定）。
- 不做远程数据库初始化/迁移、域名/HTTPS/反向代理配置。
- 不做私有仓库凭证管理（只支持公开仓库和本机已配好凭证的仓库）。
- 不做多主机/多实例批量部署、不做定时自动部署。
- 不改动 ai-core（packages/termmind-ai-core）、dsh、旧前端；浏览器端不提供部署能力（提示使用桌面版）。

## 1. 总体架构

新增后端包 `com.termmind.server.deploy`。部署运行**复用现有对话主循环**（ChatService + AgentLoop + 事件日志 + SSE），不另起编排引擎：AI 在对话里决策每个阶段执行什么，后端用一个**部署记录（DeployRun）**作为权威进度账本，前端从该账本投影阶段卡片。

### 1.1 新增组件

| 组件 | 位置 | 职责 |
|---|---|---|
| `WorkspaceStore` | deploy | 工作区 CRUD，canonical 路径去重，SQLite 持久化 |
| `WorkspaceController` | deploy/controller | 工作区列表/选择/移除/重命名 REST 端点 |
| `LocalExecService` | deploy | 本机进程执行，cwd 锁死工作区，路径越界拒绝 |
| `LocalJobManager` | deploy | 本机长命令异步作业（模式照搬 SshJobManager） |
| `DeployRunStore` | deploy | 一次部署的权威账本：阶段、状态、命令、输出摘要、产物、远程路径 |
| `DeployController` | deploy/controller | 部署记录查询、单步重试等 REST 端点 |
| `LocalCommandClassifier` | deploy | 本机命令风险分级：ALLOW / CONFIRM / DENY |
| `RunLocalAsyncTool` | deploy | AI 工具：异步执行本机命令 |
| `LocalJobPollTool` | deploy | AI 工具：轮询本机作业状态与输出 |
| `EditLocalFileTool` | deploy | AI 工具：修改工作区内文件（构建排错用，每次需确认） |
| `DeployUploadTool` | deploy | AI 工具：本地路径 → 流式 SFTP 直传 |
| `DeployStageTool` | deploy | AI 工具：声明阶段推进/阶段结论 |

### 1.2 复用的现成能力

- `SshSessionManager.exec`：远程同步命令执行。
- `RunSshAsyncTool` + `SshJobManager` + `SshJobPollTool`：远程长命令（远程构建/解压/启动）直接复用。
- `SftpService.putStream(sessionId, dir, filename, InputStream, monitor)`：GB 级流式直传，只开一次 SFTP put。
- `PermissionEngine`（ai-core，只读使用）+ `PendingInteractionHub` + `AgentConfirmController`：审批挂起/确认回路。
- `SessionCommandGrants`：会话内「相同操作不再询问」。
- `LocalAttachmentRegistry` 的授权根机制：扩展为工作区授权根。
- Electron 主进程 `selectWorkspace` IPC、preload `electronAPI`。
- 会话事件日志（SessionEventManager/Store）：部署阶段事件走既有事件通道推送，前端无需新的实时通道。

### 1.3 关键设计取舍

第一刀的阶段状态机是**「可回退的进度账本」，不是硬门禁**：AI 用 `deploy_stage` 声明进入哪个阶段，后端记录并推送；构建失败修复后可重新回到构建阶段。这样既有确定的进度外壳，又不会因顺序校验卡死 AI 排错。跑过若干真实项目、高频模式清晰后，第二刀再把常见类型（Spring Boot、Vite 前端、静态站）固化为模板。

## 2. 阶段模型（用户看到的 7 步）

```
① 选项目 → ② 看懂项目 → ③ 准备环境 → ④ 构建打包
→ ⑤ 确认产物 → ⑥ 上传服务器 → ⑦ 远程启动与验证
```

| 阶段 | 小白看到的文案 | AI/后端在做什么 |
|---|---|---|
| ① 选项目 | 「选择一个项目文件夹，或粘贴 Git 地址」 | 本地目录选择 / git clone；登记工作区与授权根 |
| ② 看懂项目 | 「这是一个 Java 后端项目（Maven）」 | 读 package.json/pom.xml/build.gradle 等，输出大白话项目说明与部署计划 |
| ③ 准备环境 | 「正在检查电脑上的 Java、Node…」 | 检查本机 JDK/Node/git；Git 入口时完成 clone；缺运行时给出处理选项 |
| ④ 构建打包 | 「正在下载依赖…」「正在打包…」 | 执行 install/build；日志实时滚动但默认折叠；失败时 AI 读尾部日志排错 |
| ⑤ 确认产物 | 「产物：app.jar（38MB），确认上传吗？」 | AI 列出产物绝对路径与大小；**唯一固定人工停顿点** |
| ⑥ 上传服务器 | 进度条 + 「正在上传到 /opt/termmind-apps/…」 | 后端内部流式直传；默认目录可改 |
| ⑦ 远程启动与验证 | 「✅ 已启动，访问 http://host:port」 | 解压、远程运行时检查、nohup 启动、端口探活 |

阶段状态：`pending / running / done / failed / skipped`。失败时该步变红，卡片提供「重试这一步」（等价自动发送「修复后重试此步骤」），已成功阶段不重跑。

## 3. 工作区模型

### 3.1 两个入口

UI 上为 dsh 风格的「项目」选择器（侧边栏/顶栏入口）：

1. **选择本地目录**：桌面端调 `electronAPI.selectWorkspace()` 弹原生目录对话框；后端 realpath 规范化 → 校验存在且为目录 → 写入 `workspaces` 表（canonical 路径重复则直接复用）→ 注册为授权根。
2. **从 Git 拉取**：输入仓库 URL + 可选分支 → LocalExecService 在 `<userData>/projects/` 下执行 `git clone` → clone 成功后自动登记工作区。

### 3.2 授权根语义

工作区登记后成为该会话本机操作的唯一授权根：

- `read_local_file`、`run_local_command`、`edit_local_file` 的所有路径解析后必须位于工作区内，越界一律 403（沿用 LocalFileReadTool/白名单的 fail-closed 模式）。
- 命令执行的 cwd 固定为工作区根（或其内部子目录）。
- 切换工作区 = 切换授权根；一次部署绑定创建时的工作区，不受之后切换影响。

### 3.3 持久化

`workspaces` 表字段：id、canonical_path、title（默认目录名，可改，允许重名）、source（local/git）、git_url、created_at、last_used_at。列表按 last_used_at 倒序；移除工作区只删记录，不碰磁盘文件。

## 4. 本机执行能力

### 4.1 LocalExecService

- 基于 `ProcessBuilder`；Windows 下经 `cmd /c <command>` 执行（与用户手工开终端一致），POSIX 下经 `/bin/sh -c`。
- `directory(workspaceDir)`：cwd 锁死工作区；不继承会泄漏凭据的自定义环境，只保留必要系统环境（PATH、JAVA_HOME、SystemRoot、用户目录变量）。
- 同步执行仅用于秒级命令（`java -version`、`node -v`、`git --version`、`dir/ls`），超时 30s。

### 4.2 LocalJobManager（照搬 SshJobManager 模式）

- `start(command, tag)` 立即返回 job_id；进程在独立 daemon 线程运行，不占用工具线程池。
- 有界输出：保留开头 256KB + 结尾 64KB（环形），总输出计数；防止大日志撑爆内存与模型上下文。
- 单任务上限 60 分钟，到时杀进程并置 FAILED；结束后记录保留 30 分钟，懒清理。
- 作业状态仅在内存：服务重启后作业消失，相关阶段标记为 interrupted（见第 7 节）。
- 进程销毁只按本进程树处理（ProcessBuilder 持有子进程引用），不使用 taskkill 级联通配。

### 4.3 AI 工具

- `run_local_async`（EXECUTE 类，与远程 run_ssh_async 命名对齐）：入参 command、purpose（大白话用途，必填，用于确认卡展示）；先经 LocalCommandClassifier 分级。
- `local_job_poll`（READ 类）：长轮询作业，返回状态/退出码/输出尾部。
- `edit_local_file`（WRITE 类，构建排错）：路径必须在工作区内；文本文件写入（上限 1MB）；每次调用走确认，卡片显示「AI 想修改 `<文件>`，原因：…」。

## 5. 审批分级

### 5.1 三级分类（LocalCommandClassifier）

**ALLOW（自动执行，不打断用户）**——白名单前缀/模式：

- 环境检查：`java -version`、`node -v/-version`、`npm -v`、`git --version`、`mvn -v` 等只读版本命令
- `git clone/status/log/diff`（clone 目标限定在统一 projects 目录内）
- 包管理安装/构建：`npm/pnpm/yarn install`、`npm/pnpm/yarn run build`（及常见 build 别名）、`mvn package/compile`（允许 -DskipTests）、`gradle build/bootJar`
- 工作区内只读/目录命令：`dir/ls/cd/pwd/echo/mkdir`

**DENY（硬拒绝，与信任级别无关）**：

- Windows：`format`、`del/erase /s` 指向工作区外、`reg`、`diskpart`、`shutdown`、`wmic` 删除类、PowerShell `-enc` 混淆执行
- POSIX：`rm -rf` 指向工作区外或指向 `/`、`mkfs`、`dd of=/dev/`、`shutdown`、`iptables`
- 通用：`curl|sh`、`wget|bash` 远程脚本管道、sudo/su 提权、写入工作区外的路径、管道中夹带 DENY 片段

**CONFIRM（默认兜底，fail-closed）**：

- 白名单未命中的一切命令 → 弹确认卡，不做「猜它安全」的放行。
- 确认卡内容：命令原文 + AI 必填的 purpose（大白话用途）+ 风险提示（如「此命令会下载并安装软件」「会修改项目文件」）。
- 远程命令另有第 6 节护栏，分级逻辑相同。

### 5.2 复用机制

- 挂起/回传：`PendingInteractionHub.awaitSessionConfirm` + `AgentConfirmController` 现成回路（10 分钟超时按拒绝）。
- 「不再询问」：用户勾选后由 `SessionCommandGrants` 记录（会话内、命令文本精确匹配），不做前缀匹配。
- AI 被拒绝后应换方案或向用户解释，不允许重试同一被拒命令绕过。

## 6. 远程服务器护栏（重点防止搞挂用户服务器）

### 6.1 目录约定

- 应用优先放在 `/opt/termmind-apps/<app-name>/`（部署前允许用户改一次）；不向系统目录写任何东西。若普通用户对 /opt 无写权限，自动回退到 `~/termmind-apps/<app-name>/` 并在卡片上明确告知实际目录，不弹 sudo 提权。
- 每次部署目录结构：

```
/opt/termmind-apps/<app>/
  current/        # 当前版本（产物解压处）
  previous/       # 上一版（新版本验证通过后才清理；清理本身需确认）
  run.pid         # 当前进程 pid
  console.log     # nohup 输出
```

- 上传包先落到 `current` 旁的临时目录，解压成功后再原子切换（mv），避免半截文件被启动。

### 6.2 复用既有删除护栏

`PermissionEngine` 已有远程路径分级：对 `/boot /usr /bin /sbin /lib /proc /sys /dev` 整树删除硬 DENY；对 `/home /root /var /opt /srv /usr/local` 删除强制 CONFIRM。部署内的清理只允许在本应用目录内进行；覆盖已有应用 = 强制确认。

### 6.3 运行时与端口

- 启动前远程检查 `java -version` / `node -v` 是否满足项目要求：
  - 缺失时**不自动安装**，弹确认卡解释「需要在服务器安装 OpenJDK 17，将执行 apt/yum 命令」，用户批准后才执行；优先方案第二刀再做（用户目录级免 root 安装）。
- 端口由 AI 在阶段②从配置中读出并在阶段⑤让用户确认：
  - 启动前检查端口占用；被占用时**绝不自动 kill 他人进程**，改为询问用户（换端口 / 用户自行处理）。

### 6.4 启动与停止

- 第一刀统一用 `nohup <启动命令> > console.log 2>&1 &` 并立即 `echo $!` 记录 pid 到 run.pid。
- 停止/重启只按 run.pid 精确 `kill`（先 TERM 等待，不做 `pkill -f` 宽匹配）。
- 启动后探活：等待最多 30s，轮询 `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:<port>/`（或检查进程存活 + 端口监听）；探活失败自动读 console.log 尾部 4KB 反馈排错，不清理现场。
- 成功后回显：访问地址（公网 IP + 端口）、日志位置、停止方式。

### 6.5 注入与转义

- 所有进入远程命令的路径/文件名参数统一单引号转义（沿用 `SftpService` 现有 `replace("'", "'\\''")` 模式）；应用名只允许字母数字、短横线、下划线。
- AI 生成的 systemd/脚本类内容第一刀不落盘执行。

## 7. 数据模型

新增表（在 `Database.initSchema` 追加 CREATE TABLE IF NOT EXISTS，沿用现有风格）：

**workspaces**

```sql
CREATE TABLE IF NOT EXISTS workspaces (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  canonical_path TEXT NOT NULL UNIQUE,
  title TEXT NOT NULL,
  source TEXT NOT NULL,           -- local / git
  git_url TEXT,
  created_at INTEGER NOT NULL,
  last_used_at INTEGER NOT NULL
);
```

**deploy_runs**

```sql
CREATE TABLE IF NOT EXISTS deploy_runs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  workspace_id INTEGER NOT NULL,
  session_id TEXT NOT NULL,
  host_id INTEGER NOT NULL,
  current_stage TEXT NOT NULL,          -- select..verify 七阶段标识
  stages_json TEXT NOT NULL,            -- 每阶段 status/command/purpose/输出摘要/时间
  plan_json TEXT,                       -- AI 在阶段②给出的部署计划（大白话）
  artifact_json TEXT,                   -- 产物：本地路径、大小
  remote_app_dir TEXT,                  -- /opt/termmind-apps/<app>
  remote_pid INTEGER,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);
```

- 阶段推进 = 一次 stages_json 更新 + 写一条部署阶段事件到既有 session_events（前端 SSE 实时收到）。
- 「重试这一步」：前端调用 DeployController，重置该阶段状态并向会话注入一条系统消息触发 AI 继续，不改写此前阶段记录。

## 8. 错误恢复

| 故障 | 行为 |
|---|---|
| 本机命令非零退出 | 阶段④标 failed；AI 用 poll 读输出尾部自行排错；需要改代码时经 edit_local_file 确认后修改，再重跑 |
| 后端重启 | 内存作业消失，DeployRun 仍在；运行中的阶段标 interrupted；恢复后从最后成功阶段继续，不重头跑 |
| SSH 断开/超时 | 阶段⑥⑦提示重新连接主机（沿用现有「尚未连接」重连卡）；已上传文件不重复传（先 stat 比对大小） |
| 上传中断 | deploy 直传为单次 put，中断后整包重试（部署包通常几十 MB）；2GB 级手动上传仍走分片通道 |
| 远程启动失败 | 保留现场（进程、日志、previous/），读 console.log 尾部反馈；用户可选择「重试启动」或回退到 previous（mv 切回，需确认） |
| 用户拒绝命令 | AI 收到拒绝结果，换方案或停止并解释；不重复弹同一命令 |

## 9. 前端（v2）要点

- `WorkspacePicker`：dsh 风格项目选择器（列表 + 「选择文件夹」「从 Git 拉取」两个入口），黑白单色、紧凑。
- `DeployStageCard`：七步纵向进度卡（图标 lucide，运行中可加轻量动画），阶段⑤内嵌「确认上传 / 改远程目录」操作；失败态内嵌「重试这一步」。
- 构建日志：卡片内折叠区，展示 LocalJob/SshJob 轮询输出的尾部。
- 浏览器端：所有部署入口置灰并提示「请使用桌面版」。
- 部署数据从现有会话事件 + DeployController 查询获得，不新增实时通道。

## 10. 测试策略

### 10.1 后端单测

- `LocalCommandClassifierTest`：ALLOW 白名单命令、DENY 各形态（含工作区外 rm、curl|sh、sudo）、CONFIRM 兜底，含 Windows/POSIX 两套。
- 路径越界测试：工作区外的 read/edit/执行路径一律拒绝。
- `DeployRunStoreTest`：阶段推进、失败重试状态重置、stages_json 序列化兼容。
- 本机作业集成测试：执行 `echo`/`dir` 等无害命令验证 job 生命周期与有界输出。

### 10.2 手工验收（用户执行，不连真实生产服务做自动化）

准备三个最小项目：静态站（一个 index.html）、Vite 示例项目、Spring Boot Maven 示例。

1. 本地目录入口：选目录 → AI 说明项目类型 → 构建 → ⑤确认 → 上传 → 启动 → 浏览器打开回显地址。
2. Git 入口：粘贴公开仓库地址完成全流程。
3. 构建失败注入：制造一个明显错误，验证 AI 读日志 → 提修改 → 确认 → 重跑。
4. 审批：触发一次安装类命令确认、验证 remember 后不再弹；验证 DENY 命令被直接拒绝。
